# Research: SOP confirmation and resumable TeamAgent runs

- Query: Trace current chat/API/frontend streaming and persistence patterns for a structured TeamAgent SOP, explicit confirmation, pause/resume, rejection/edit behavior, and visible run state.
- Scope: mixed (internal code and tests; no external references required)
- Date: 2026-08-03

## Findings

### Current TeamAgent execution and checkpoint boundary

- The outer TeamAgent graph is a single `agent` node (`START -> team_router_node -> END`) and is compiled with `checkpointer=None`; the source explicitly says the outer graph is stateless and that only the inner deep-agent checkpointer persists conversation history. See `src/agents/team_agent/graph.py:77-108`.
- The TeamAgent stream creates an outer task for `self._graph.ainvoke`, tracks it by `presenter.run_id`, and yields only metadata/error/goal/done lifecycle events around that task (`src/agents/team_agent/graph.py:110-237`). There is no outer plan/approval state or interrupt/resume branch.
- `team_router_node` builds custom subagents from every `team.active_members`, then falls back to a single `general-purpose` subagent when none are configured (`src/agents/team_agent/nodes.py:399-486`). It passes that list directly into `create_deep_agent(..., subagents=custom_subagents, checkpointer=inner_checkpointer)` (`src/agents/team_agent/nodes.py:544-552`). This is the existing roster construction point for deterministic SOP role selection.
- The inner graph receives the user message and attachment-derived message, then starts `inner_graph.astream_events(...)` immediately (`src/agents/team_agent/nodes.py:632-679`). No structured plan is emitted or gated before this call. The returned state only contains `output` and an empty `messages` list because history is delegated to the inner checkpointer (`src/agents/team_agent/nodes.py:696-706`).
- Existing TeamAgent tests verify sandbox backend selection and that the deep-agent factory receives a backend, but do not assert confirmation gating, role task suppression before approval, or resume semantics (`tests/agents/test_team_agent_sandbox_support.py:1-238`).

### Chat submission, stream, status, cancel, and resume APIs

- `POST /api/chat/stream` creates a unique `run_id`, stores attachments and all agent/team options in queued task context, and returns session/run/trace metadata with `status: pending` (`src/api/routes/chat.py:349-615`). This is the natural entry point for a planning run, but currently starts the normal executor path.
- `GET /api/chat/sessions/{session_id}/stream?run_id=...` reads the run-specific Redis stream and emits SSE until `complete`/`error` (or stream exhaustion). It validates session ownership, uses `dual_writer.read_from_redis(session_id, run_id=run_id)`, sends heartbeat comments, and formats each event with `event`, JSON `data`, and Redis event `id` (`src/api/routes/chat.py:616-707`).
- `GET /api/chat/sessions/{session_id}/status` returns `TaskStatus.value` and an error for a requested run or current session run (`src/api/routes/chat.py:709-744`). Existing enum values are queued/pending/starting/running/cancelling/cancelled/completed/failed/recovering/expired (`src/infra/task/status.py:7-18`); there is no `awaiting_confirmation` status.
- `POST /api/chat/sessions/{session_id}/cancel` delegates to `TaskManager.cancel`, including queued-task removal (`src/api/routes/chat.py:746-786`). `POST /api/chat/sessions/{session_id}/resume` delegates to `TaskManager.resume_session` (`src/api/routes/chat.py:788-803`).
- Recovery is implemented as a new run from the prior run's latest checkpoint, with `resumed_from_run_id` metadata and a distributed Redis lock. It marks the source failed/recovering, submits a new executor task, and restores a recoverable failure on error (`src/infra/task/recovery.py:344-424`). `resume_session` refuses completed or user-cancelled tasks and otherwise resumes the session's current run (`src/infra/task/recovery.py:444-497`). This is reusable for crash recovery but is not a user plan-confirmation resume: it cannot apply edited plan input and the recovery message is generated internally.

### Event transport and durable persistence

- Presenter events are normalized by `_build_event`, which adds `depth` and `agent_id` to dict payloads and keeps event data structured (`src/infra/writer/presenter_events.py:58-125`). Existing event constructors include message chunks, summaries, tool start/result, sandbox states, todos, and `approval_required` (`src/infra/writer/presenter_events.py:120-180`, `src/infra/writer/presenter_events.py:383-424`).
- `approval_required` currently carries an approval id, question/message, type, choices/default, timestamp, depth, and agent id; this is a viable transport shape to extend with `plan_id`, structured SOP payload, and correlation fields (`src/infra/writer/presenter_events.py:383-424`).
- `Presenter.save_event` writes every event to the dual writer with `session_id`, `trace_id`, `agent_id`, and `run_id`; `Presenter.complete` flushes Mongo and marks trace status (`src/infra/writer/presenter_storage.py:141-190`).
- `DualEventWriter.write_event` writes immediately to Redis for live SSE and buffers Mongo writes; the Mongo event document stores `event_type`, `data`, timestamp, and a session-global `seq` (`src/infra/session/dual_writer.py:194-263`; `src/infra/session/trace_storage.py:316-358`).
- Session history reads aggregate trace events by `session_id`/`run_id`, preserve causal order with `seq`, and default to excluding `status: running` traces (`src/infra/session/trace_storage.py:750-865`). The session route exposes this via `GET /api/sessions/{session_id}/events`, with run/event-type filters and bounded limits (`src/api/routes/session.py:274-343`). A plan awaiting confirmation must therefore either be persisted in a non-terminal trace or have an explicit status/event read path; the current completed-only default would hide a running/paused plan from history.
- Existing event fixture coverage includes `approval_required`, `agent:call`, `agent:result`, `todo:updated`, `complete`, `done`, errors, queue updates, sandbox, and user message/cancel events, demonstrating the established machine-readable event vocabulary (`tests/events/stream_events.json:1-210`).

### Existing human approval / explicit response pattern

- `create_approval` persists a pending approval in Mongo, creates a bounded local `asyncio.Event` cache entry, and notifies the frontend (`src/api/routes/human.py:103-145`). `wait_for_response` first checks Mongo, then waits on both local and distributed notification paths, with timeout and cleanup (`src/api/routes/human.py:147-220`).
- `POST /api/human/{approval_id}/respond` accepts `approved` plus a JSON response query value, validates pending state, updates Mongo, publishes a distributed response, and wakes local waiters (`src/api/routes/human.py:245-284`). Rejection is represented as `approved=false` / status `rejected`; there is no first-class plan-edit payload contract beyond the generic response object.
- The `ask_human` tool creates an approval, emits `approval_required` through SSE, blocks on `wait_for_response`, and returns `success`, `rejected`, or `timeout` JSON to the model (`src/infra/tool/human_tool/tool.py:156-205`). This is the closest existing pause/resume implementation. However, it pauses inside a model tool call and cannot ensure that no other role task was started before the call; a TeamAgent SOP gate should happen before deep-agent subagent dispatch.
- Approval tests cover distributed wait cleanup, JSON response parsing, and bounded local event cache (`tests/api/routes/test_human_wait.py:1-154`) and tool tests cover approval response/rejection result formatting (`tests/infra/tool/test_human_tool.py:1-105`).

### Frontend stream/state/reconstruction patterns

- `useAgent` submits `/api/chat/stream`, receives `session_id`/`run_id`, then connects to run-scoped SSE via `fetchEventSource` at `/api/chat/sessions/{session_id}/stream?run_id=...` (`frontend/src/hooks/useAgent.ts:680-810`; `frontend/src/hooks/useAgent/sseConnection.ts:140-220`).
- The frontend parses every SSE event, deduplicates by event id and timestamp, drops events older than loaded history, and caps dedup memory (`frontend/src/hooks/useAgent/eventHandlers.ts:53-105`). This provides a safe event-id/sequence basis for new plan and role-progress events.
- Known event types are a closed TypeScript union including `approval_required`, `agent:call`, `agent:result`, `todo:updated`, sandbox, queue, complete/done/error, but no SOP/plan/role-progress/awaiting-confirmation types (`frontend/src/hooks/useAgent/types.ts:8-28`). `EventData` already has generic `id`, `message`, `choices`, `default`, `depth`, `agent_id`, `run_id`, todo and attachment fields (`frontend/src/hooks/useAgent/types.ts:39-125`).
- `approval_required` is handled as a side effect: the client fetches `/human/{id}`, adds only pending approvals through `onApprovalRequired`, and does not transform the event into message content (`frontend/src/hooks/useAgent/eventHandlers.ts:246-270`, `frontend/src/hooks/useAgent/eventHandlers.ts:507-535`). History loading repeats this lookup for persisted approval events (`frontend/src/hooks/useAgent/historyLoader.ts:101-145`).
- `useApprovals` loads `/human/pending` on session load, deduplicates incoming SSE approvals, and responds with `approved` and a JSON response via `/human/{id}/respond`; it removes the approval from local state after a successful response (`frontend/src/hooks/useApprovals.ts:10-96`). `ApprovalPanel` renders markdown/form fields, countdown/extension behavior, and approve/reject controls (`frontend/src/components/panels/ApprovalPanel.tsx:195-260`). This panel can be adapted for structured SOP review/edit, but its `PendingApproval` type currently only supports form approvals (`frontend/src/types/message.ts:226-238`).
- Session history loads events and status in parallel, reconstructs messages from persisted events, reconnects SSE when status is pending/running, and restores goals from `goal:start`/`goal:end` (`frontend/src/hooks/useAgent.ts:367-499`). It does not treat a paused/awaiting-confirmation status as active and would not reconnect a run with a new status unless that condition is added.
- Frontend state conventions favor local `useState` for form/loading/modal state and typed API modules; no global state library is used (`.trellis/spec/frontend/state-management.md:1-96`). High-frequency stream snapshots should use immutable references and frame-coalesced external stores when needed, but plan approval is low-frequency and can remain local or session-scoped.

### Existing frontend API surface and tests

- `frontend/src/services/api/session.ts` has typed helpers for session events, runs, status, cancel, and chat submission, but no resume helper and no plan/approval mutation helper (`frontend/src/services/api/session.ts:1-280`).
- Session API tests validate bounded event/run queries and URL construction; they do not cover plan state, confirmation, or resume (`tests/api/routes/test_session_runs.py:1-340`, `frontend/src/services/api/__tests__/session.test.ts`).
- SSE tests verify retrying an early close and distinguishing transport errors from terminal events (`frontend/src/hooks/useAgent/__tests__/sseConnection.test.ts:1-40`). New plan gating should extend the same terminal/reconnect tests and assert no role task event appears before confirmation.

## Implications for the requested SOP flow

1. Reuse the existing run-scoped SSE + dual Redis/Mongo event contract. Emit a structured `plan:proposed` (or equivalent) event containing a stable plan id, ordered steps, role/persona ids and versions, dependencies, artifact requirements, criteria, attachment manifest, and `awaiting_confirmation` state. Persist it through Presenter so history can reconstruct it.
2. Add a plan confirmation endpoint (or a dedicated approval record) keyed by session/run/plan id. The current human approval store is durable and distributed, but generic `approved/response` must be constrained by plan id and support edit/reject semantics. Do not rely only on model `ask_human`, because it is invoked after model execution has already begun.
3. Gate inner deep-agent invocation in `team_router_node` (or a dedicated outer TeamAgent planning node) until confirmation is accepted. The outer graph currently has no checkpointer, so a true pause should either persist an explicit plan/run state and return, then start a new confirmed run, or compile an outer checkpointer/interrupt contract. The existing recovery API is crash-oriented and should not be conflated with approval resume.
4. Introduce an explicit status (for example `awaiting_confirmation`) in backend `TaskStatus`, status route, frontend history reconnect logic, and UI state. Keep `rejected`, `edited`, `cancelled`, `partial_failure`, `retrying`, and `completed` distinguishable through events/status rather than inferred from message text.
5. Extend the frontend event union and history reconstruction with plan/role event types. Existing event-id/timestamp deduplication, run filtering, and session-global event sequence support reconnection and page refresh. The current `ApprovalPanel` can be the interaction shell, but plan editing needs typed fields for step order, role assignment, dependencies, and attachment paths.
6. Preserve existing recovery metadata (`resumed_from_run_id`) for crashes and partial failures, and include plan id/version and correlation ids in any confirmed/retry run so the UI can relate a new run to the reviewed plan.

## Caveats / Not Found

- No current TeamAgent SOP/plan schema, plan event type, `awaiting_confirmation` task status, role-progress event contract, or plan-specific API was found.
- The outer TeamAgent graph's `checkpointer=None` means LangGraph interrupt/resume cannot be assumed at the TeamAgent boundary; only the inner deep-agent conversation checkpoint is currently available.
- Session history defaults to `completed_only=True` and frontend reconnect checks only `pending`/`running`; paused plans require explicit status/read-path changes to survive refresh.
- Existing human approvals are generic form approvals and their API uses query parameters, so plan edits should not be silently encoded as arbitrary fields without validation and idempotency.
- `tests/events/stream_events.json` is a fixture, not a protocol schema; adding entries there alone will not make frontend/backend behavior compatible.
