# 定时任务二期：选择专家、定时运行不注入 ask_human/SOP、聊天中管理、管理员管控

## Goal

在一期定时任务（`.trellis/tasks/09-30-scheduled-tasks/`，提交 `6db75a14`，分支 `feat/scheduled-tasks`，尚未合入 main）的基础上补齐五件事：

- 定时任务能指定由哪位专家去执行；
- 定时触发的那一轮不提供 ask_human 和 SOP 确认工具，不会卡住等人；用户之后续聊时恢复正常；
- 用户能从运行结果进入会话接着聊，这些会话和普通会话一样受 checkpoint 保留期清理；
- 能在聊天里查询、创建、修改定时任务，确认后才生效；
- 管理员能控制谁能用、查看并干预所有人的任务，并防止定时任务挤占聊天主链路。

统计沿用现有口径（R6）。

调研依据见 `research/`，包括 `persona-selection.md`、`unattended-isolation-and-session.md`、`chat-tool.md`、`admin-governance.md`。

## Background（现状与代码证据）

- **专家**
  - 后端已有 `persona_preset_id` 字段，runner 也会解析专家快照（`src/infra/scheduler/runner.py` `_execute`）。
  - 但编辑器保存时只提交 name、prompt、schedule、timezone、template_id（`TaskEditorDialog.tsx` `save()`），service 也不校验专家（`service.py:77,105`）。
  - 与聊天相比，runner 有三处缺口：
    - 不注入专家知识库（chat 侧见 `chat.py:403-408`）；
    - 不把专家的 `skill_names` 作为 `enabled_skills` 传入（Web 端由前端 `useAgent.ts:645` 发送）；
    - 专家失效时返回英文 `persona_preset_not_found`，并且会被重试、计入连续失败。
  - 可见性规则在 `persona_preset/manager.py:129-142`，校验应使用 `get_preset`（`manager.py:213`）。不能用 `use_preset`，它会累加使用次数。
- **人工交互**
  - 全仓只有两处会等人：
    - `ask_human`（`src/infra/tool/human_tool/tool.py`）：默认等 300 秒，最长可设 3600 秒，超时后按默认值继续；
    - 团队 SOP 确认门禁（`src/agents/team_agent/sop/tool.py`）：等 300 秒。
  - 工具注入的位置：
    - fast / search 每一轮都无条件注入 ask_human（`fast_agent/context.py:162`、`search_agent/context.py:179`）；
    - `update_sop` 只在团队智能体中追加（`team_agent/nodes.py:346-351`）；
    - 专家的偏好智能体只能是 fast 或 search（`persona_preset.py:11`）。
  - 项目里没有「无人值守 / 非交互」这类运行状态（全仓 grep 无结果）。定时运行目前和聊天完全一样：会注入 ask_human，一旦调用就挂起并占用执行槽。
  - 子代理提示词里提到了 ask_human（`subagent_prompts.py:37`）。
  - 已有现成的工具排除做法，可直接参照：
    - 团队模式的 `TeamToolExclusionMiddleware`（`team_agent/tool_exclusion.py`）在模型请求这一层按名称过滤工具，主代理和子代理都挂了这个中间件（`team_agent/nodes.py:407,600`）；
    - `MCPQuotaMiddleware.awrap_tool_call`（`tool_interception.py:232`）在工具执行这一层拦截调用，直接返回提示。
- **定时会话**
  - checkpoint 的 thread_id 等于 session_id，打开 `/chat/sch_*` 能续聊，上下文连续。
  - 会话带有 `hidden_from_conversation_list`，过滤只在 `list_sessions` 中生效（`session/storage.py:384`），所以续聊后会话仍不会出现在侧边栏。
  - 每次运行结束都会同时推送 `task:complete`（`executor.py:397-430`）和 `scheduled_task:run_finished` 两条通知。
  - 服务重启后，启动恢复会续跑中断的运行（`task/startup_cleanup.py`），续跑时不知道这是一次定时运行。
- **checkpoint 清理**
  - `list_inactive_session_ids`（`session/storage.py:721`）不过滤 hidden，所以定时会话会按保留期被清理，清理后的「只读」体验也同样适用。
  - `CHECKPOINT_CLEANUP_ENABLED` 默认关闭（`kernel/config/base.py:233`），默认每 24 小时清一批、每批 200 个。
- **统计**
  - 定时运行的 user:message 与 `record_message_activity` 各写一次（`task/manager.py:143-149`），专家归属以会话 metadata 为准，无需改统计代码。
  - 重试时每次尝试都是新会话（`_rN`），会多计会话数与消息数。
- **管控**
  - 现有设置项只有 3 个：总开关、每人上限、最小间隔（`_definitions_extra.py:708-731`）。
  - 总开关关闭时没有端到端生效：
    - 侧栏入口仍然显示（`SessionSidebar.tsx:118-123` 写死 `show: true`）；
    - 仍然可以创建任务（`service.py:77`）；
    - 开关「开→关→开」后任务不会重新注册（`service.py:244-249` 关闭分支不重置 `_marker`，探针已复现）。
  - 路由只依赖 `chat:write`（`routes/scheduled_task.py:29`）。
  - 运行时不复核创建人是否已停用或无权限（`runner.py` `_resolve_owner`）。
  - 定时运行不经过按用户的并发限制，也没有全局并发上限，并与聊天共用 arq 队列（`max_jobs=64`）。
- **权限**
  - 仓库没有权限迁移机制。admin 是 `is_system` 角色，每次启动刷新为拥有全部权限（`role/storage.py:483-508`）。
  - 已部署环境中的普通角色不会自动获得新权限。先例 `68c909a4`（专家）、`789f269d`（通知）都没有补授予。

## Requirements

### R1 定时任务选择专家

- R1.1 编辑器新增「执行专家（可选）」，可从当前用户可用的专家中选择，也可清除。复用现有专家选择器；用户没有 `persona_preset:read` 权限时隐藏该项。
- R1.2 保存时校验专家可用，可见性规则与聊天一致：自建专家仅本人可用，全局专家需已公开且已发布，管理员可用全部。不可用时返回中文 400。
- R1.3 任务卡片显示专家名称和头像；专家失效时显示「专家已不可用」。
- R1.4 执行时与在聊天中使用该专家完全一致，包括系统提示词、专家技能、专家偏好的智能体模式和专家知识库。每次执行取专家的最新版本。
- R1.5 专家被删除、下架或用户已无权使用时，本次运行失败，提示「所选专家已被删除、下架或你已无权使用，请编辑任务更换专家」。该失败不重试，任务立即暂停并显示这一原因。
- R1.6 本期不提供智能体模式、团队、模型的选择入口。任务的 `agent_id` 只允许 `fast` / `search`：有专家时由专家决定，没有专家时为 `fast`。

### R2 定时运行不注入 ask_human 和 SOP 工具

- R2.1 定时触发和「立即执行」产生的那一轮运行，带上「定时运行」标记（代码字段 `unattended`）。这个标记只对这一轮有效，不随会话继承；用户之后在同一会话里续聊的运行不带该标记。
- R2.2 定时运行中，ask_human 对模型不可见（主代理和子代理都一样）。如果模型仍然调用，调用会被拦下，返回「不能提问」的提示，不会创建审批，也不会等待。用户之后续聊时恢复正常。实现方式参照团队模式现有的工具排除中间件。
- R2.3 定时运行中，SOP 确认工具（`update_sop`）按同样方式排除。定时任务只运行 fast / search 智能体（R1.6），本来就不会用到这个工具，这里排除是作为保险。
- R2.4 定时运行的系统提示词加一段说明：「这是定时任务自动执行，用户不在场，不能向用户提问；不执行不可逆或有外部副作用的操作；需要用户确认的事项写在回答末尾」。这段说明不写入会话消息，也不进入 checkpoint。
- R2.5 定时运行如果因服务重启中断，不自动恢复，交给定时任务自己的失败与重试机制处理。
- R2.6 定时运行结束时只推送定时任务通知，不再推送通用的「任务完成」通知。

### R3 定时会话续聊与 checkpoint 清理

- R3.1 从运行记录或通知进入定时会话后可以继续对话，上下文连续，并使用该任务的专家。模型沿用会话里记录的设置，与普通会话一致。
- R3.2 用户在定时会话里首次发送消息后，该会话出现在侧边栏（取消隐藏）。没有续聊过的定时会话不出现在侧边栏。
- R3.3 定时会话与普通会话使用同一套 checkpoint 保留期清理。清理后可以查看历史，但不能继续对话或分叉，行为与普通会话一致。
- R3.4 上线清单要求生产环境开启 checkpoint 清理，并按定时运行量调整每批清理数量和清理间隔。

### R4 聊天中查询、创建、修改（不含删除）

- R4.1 提供两个智能体工具：
  - 查询我的定时任务，返回频率中文描述、下次执行时间、最近一次结果；
  - 生成创建或修改的草稿，修改包括改内容、改时间、改专家、暂停、恢复。
- R4.2 创建和修改只能由用户在草稿卡片上点击「确认」后生效（D8）。智能体没有确认工具，也无法代替用户确认；用户可以在卡片上取消。草稿 30 分钟内有效。
- R4.3 草稿展示名称、要做的事、频率中文描述、接下来 5 次执行时间和执行专家；修改时同时展示改动前后。
- R4.4 新建任务默认使用当前对话的专家。用户也可以按名称指定专家；名称有歧义时列出候选，让用户选择。
- R4.5 校验规则与网页端一致：每人上限、最小间隔、不能选过去的时间、专家必须可用。错误信息一律为中文。工具内部异常不外泄，也不会因为重试导致重复创建。
- R4.6 定时运行和团队智能体中不提供这些工具。企业微信会话只提供查询工具：企业微信里无法渲染确认卡片，需要创建或修改时引导用户到网页端。
- R4.7 管理员可以单独关闭「聊天中管理定时任务」；总开关关闭时，这些工具也一并不可用。
- R4.8 在聊天中创建或修改成功后，定时任务页面同步刷新。任务记录来源，区分网页创建和聊天创建。

### R5 管理员管控

- R5.1 新增两个权限：「使用定时任务」（`scheduled_task:use`）和「管理所有定时任务」（`scheduled_task:admin`），可在角色管理中勾选。网页、接口、聊天工具都需要「使用」权限。
- R5.2 总开关端到端生效：
  - 关闭后侧栏入口隐藏，页面提示功能已关闭；
  - 禁止新建、修改、恢复和立即执行；
  - 已有任务停止触发，数据保留，仍可查看和删除；
  - 重新开启后任务自动恢复调度，同时修复「开→关→开」后任务不恢复的问题。
- R5.3 运行时复核创建人：账号已停用或已没有「使用」权限时，本次不执行，任务自动暂停并说明原因。
- R5.4 管理员总览页（需要「管理」权限）：
  - 查看全部用户的任务，可按任务名或创建人搜索，按状态或最近结果筛选，支持分页；
  - 可以暂停（必须填写原因）、恢复、删除、查看运行记录；
  - 被管理员暂停的任务，用户端显示暂停原因，用户不能自行恢复。
- R5.5 定时任务全局并发上限，默认 10，可配置：
  - 超过上限时排队等待，最长 20 分钟；
  - 等待超时记为「跳过（系统繁忙）」，不计入连续失败；
  - 执行超时从真正开始执行时计算。
- R5.6 新增设置项：聊天中管理开关、全局并发上限、排队最长等待时间。现有的「每人上限」「最小间隔」补充取值范围校验。

### R6 统计

- R6.1 定时运行产生的会话、消息、Token 和专家使用量，都按普通用户会话计入现有统计，不新增区分维度，也不改统计代码。
- R6.2 把统计口径写入规范：统计查询不得过滤定时会话；重试产生的会话和消息同样计入。

## Out of Scope

- 法定节假日日历、企业微信结果推送、在聊天中删除任务。
- 模型、智能体模式、团队的选择入口；每次运行沿用同一个会话（目前每次运行都新建会话）。
- 通用审计日志集合、运行记录保留期清理、启动错峰、按用户的并发上限。
- 已清理 checkpoint 的会话应该「只读」还是「允许继续聊」：这是上次 review 遗留的问题，另行决定。本期定时会话沿用全局的行为。
- 既有问题：runner 不申请按用户的并发名额，但结束时会释放（`task/manager.py:461-503`）。本期不处理，只记录。
- 运行记录上的「需要你确认」标记：定时运行时模型看不到 ask_human，系统也就无从得知它「想问」什么，因此不提供这个标记。需要用户确认的事项写在回答末尾（R2.4）。
- 企业微信会话同样会注入 ask_human（`src/infra/agent/wecom` 中没有任何审批处理），但企业微信里没有审批界面，模型一调用就只能干等到超时。这是既有问题，本期不处理；本期新增的「定时运行」标记以后可以复用到企业微信。
- 审批面板不按会话过滤（`ApprovalPanel`）。目前审批只来自当前会话，没有实际影响，本期不处理。
