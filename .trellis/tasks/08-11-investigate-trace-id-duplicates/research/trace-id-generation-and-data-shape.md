# Research: Trace ID Generation and Duplicate Document Data Shape

- Query: Trace `trace_id` generation/propagation and identify read-only data shapes that distinguish duplicate causes.
- Scope: internal (source and Git history; no production access)
- Date: 2026-08-11

## Findings

### 1. The stored trace ID is not the HTTP correlation ID

`src/api/middleware/tracing.py:54-62` creates a request/logging ID from `X-Trace-ID` or a truncated UUID. It is returned in the response header (`:101`) and placed in `TraceContext`; there is no call path from that value into `PresenterConfig.trace_id`. A repeated client-supplied `X-Trace-ID` therefore does not, by itself, create duplicate Mongo trace documents.

The persisted ID is generated by `src/infra/writer/presenter_config.py:44-47` as `trace_<UTC microsecond timestamp>_<uuid.uuid4().hex>`. `Presenter.trace_id` lazily generates it once per Presenter (`src/infra/writer/present.py:77-86`). The UUID component has 122 random bits; accidental collision is not credible at the observed scale. For one million independent IDs, the birthday estimate is about `9e-26`; 424 duplicate groups require a reuse/write bug, not random UUID collision.

### 2. Current request-to-worker propagation intentionally reuses one ID

The normal chat path intentionally creates one ID before dispatch:

- `src/api/routes/chat.py:424-446` creates `run_id`, constructs a storage-disabled pre-Presenter, and reads `trace_id`.
- The same ID is placed in the Redis task context (`:448-465`) and passed to both `submit_arq` (`:552-574`) and local `submit` (`:576-598`).
- For queued requests, the API creates a storage-enabled Presenter with that ID and writes the user message immediately (`:507-524`). The worker later receives the same ID from `src/infra/task/arq_worker.py:89-109`.
- `BackgroundTaskManager._persist_initial_user_message` creates a trace and writes the user message (`src/infra/task/manager.py:116-147`). Since commit `dfdd45f0` (2026-05-26), both chat submit calls set `write_user_message_immediately=True` and pass `trace_id` (`git show dfdd45f0`, `src/api/routes/chat.py:552-597`). The manager performs the early create, then `TaskExecutor.run_task` receives `existing_trace_id` and creates the worker Presenter with the same ID (`src/infra/task/executor.py:61-107`, `:128-152`).
- The worker's normal completion/cancellation/error paths continue writing to the same ID (`src/infra/task/executor.py:180-211`, `:220-370`; `src/infra/writer/presenter_storage.py:159-252`).

This reuse is correct only if trace creation is idempotent. A single logical run can legitimately have several callers invoke `create_trace`; those calls must converge on one document.

Recovery and fork paths intentionally use *new* IDs:

- Recovery allocates a new run and new Presenter ID (`src/infra/task/recovery.py:148-203`), then passes it into the new task (`:222-248`); `recovery_of_run_id` is metadata, not ID reuse.
- Fork cloning generates `trace_<uuid>` for every cloned document (`src/infra/session/manager.py:509-543`). A fork should therefore produce a new session/trace pair, not a duplicate source `trace_id`.
- An ARQ retry reuses the persisted payload's `run_id` and `trace_id` (`src/infra/task/arq_worker.py:63-109`). It can repeat a create call with the same identity, but it is not a UUID collision.

Standalone agent graph fallback Presenters (`src/agents/{search,fast,team}_agent/graph.py`) generate their own ID only when no Presenter is passed. Normal TaskExecutor execution passes one Presenter, so these fallbacks are not an additional ID source in the normal chat route.

### 3. Why the historical implementation could make duplicates

Before `dd15687e` (2026-08-07):

- `TraceStorage.create_trace` used unconditional `insert_one`; it called the operation "idempotent" only because a unique index would raise `DuplicateKeyError` (`git show dd15687e^:src/infra/session/trace_storage.py`, old `create_trace` around lines 229-286).
- `DualEventWriter._build_mongo_bulk_operations` used `UpdateOne({"trace_id": ...}, ..., upsert=True)` and `$setOnInsert` (`git show dd15687e^:src/infra/session/dual_writer.py`, lines 101-142). Two bulk writers could race an absent trace and both insert when no unique index existed.
- Old index initialization launched asynchronously and swallowed index errors. `ensure_indexes_if_needed` returned `None`, `_ensure_indexes` caught exceptions as "non-critical," and the startup initializer ignored the result (`git show dd15687e^:src/infra/session/trace_storage.py`, old `ensure_indexes_if_needed/_ensure_indexes`; `git show dd15687e^:src/api/main.py`, `_init_trace_storage`). If the unique-index build failed because duplicates already existed, the process stayed up and continued writes.
- There was also a startup ordering hole: the pre-`dd15687e` initializer called `ensure_indexes_if_needed` while `TraceStorage._collection` was still `None`. The scheduled `_ensure_indexes` returned immediately on that condition, and the lazy collection getter did not schedule it again. Such a process could run for its lifetime without creating `trace_id_unique_idx`, even with an otherwise healthy MongoDB (`git show dd15687e^:src/infra/session/trace_storage.py`, old `_ensure_indexes` guard and lazy `collection` property).

The deterministic high-probability path is API/worker dual creation while the unique index was absent or failed:

1. A request generated one ID in the API.
2. The early Presenter/manager persisted the initial user message and inserted document A.
3. The worker created a Presenter with the same ID and called `create_trace`, inserting document B because old `insert_one` had no uniqueness barrier.
4. Subsequent buffered `update_one` operations matched only `trace_id`; they updated one matching source (not all duplicates), leaving another with an empty/small event array and `status=running`.

This became deterministic for both local and ARQ chat submissions after `dfdd45f0` added immediate user-message persistence. Earlier (2026-03-25 `10c106287`) the pre-generated ID and queued API pre-create already supplied the same API/worker race for queued requests.

The observed shell signature "one `completed` document with a large `event_count`, plus one `running` document with one token/event" fits this split-write shape: a completed document accumulated the main stream, while a second source remained a live/partial create. It is not proof of which process inserted each source without timestamps/logs, but it strongly rules against random UUID collision. The migration's `_is_active` sees any `status=\"running\"` source (`src/infra/session/trace_migration.py:320-340`) and skips that group by default; an apply plan must not delete the live source.

Other candidates are lower confidence:

- **ARQ retry:** same payload ID can be inserted again when a worker exception causes ARQ to retain the payload (`src/infra/task/arq_worker.py:123-139`). Look for multiple source start times and a prior `error`/terminal document. This is plausible but less deterministic than the immediate API/worker double create.
- **Bulk upsert race:** old dual-writer upsert operations can produce two event-rich documents if two processes flush the same absent ID concurrently. Look for sources with similar `started_at`, non-empty events, and sparse create metadata. This requires no early create or a race window and is secondary.
- **Cross-session reuse:** current `create_trace` validates session/run identity and raises `TraceIdentityConflictError` (`src/infra/session/trace_storage.py:636-653`). Historical code had no such validation. A cross-session duplicate would indicate manual/incorrect propagation or a stale payload, not UUID collision.
- **Fork/recovery:** current code generates new IDs and is therefore unlikely to explain duplicate source groups.

### 4. What `duplicates=424` means

The readiness preflight is `TraceStorage._find_duplicate_trace_ids` (`src/infra/session/trace_storage.py:498-507`): it matches non-null `trace_id`, groups by the ID, keeps `count > 1`, projects only `_id`, and applies `{$limit: 1000}`. `_initialize_indexes` reports `len(self._duplicate_trace_ids)` (`:450-471`) and refuses the unique index/readiness when non-empty. Thus `duplicates=424` means 424 duplicate **trace_id groups returned by that capped preflight**, not 424 extra documents and not necessarily the total if the collection has more than 1,000 groups. It excludes missing/null IDs. The exact source-document count must be obtained from a separate aggregation or the migration dry-run (`source_document_count`), and a group with three or more documents contributes one group to the 424 count.

### 5. Safe read-only Mongo discriminators

Run these against a read-only account and the trace collection configured by `MONGODB_TRACES_COLLECTION`. They only use `aggregate`/`find` and intentionally project metadata, not message content.

**A. Exact global group count and bounded sample (matches readiness semantics):**

```javascript
db.traces.aggregate([
  {$match: {trace_id: {$exists: true, $ne: null}}},
  {$group: {
    _id: "$trace_id", source_count: {$sum: 1},
    sessions: {$addToSet: "$session_id"}, runs: {$addToSet: "$run_id"}
  }},
  {$match: {source_count: {$gt: 1}}},
  {$facet: {
    summary: [{$count: "duplicate_groups"}],
    sample: [{$sort: {source_count: -1, _id: 1}}, {$limit: 50}]
  }}
])
```

The `summary.duplicate_groups` value is uncapped; compare it with the startup's capped 1,000-ID result.

**B. Same-session/run duplicates (API/worker or retry candidate):**

```javascript
db.traces.aggregate([
  {$match: {trace_id: {$exists: true, $ne: null}}},
  {$group: {
    _id: {trace_id: "$trace_id", session_id: "$session_id", run_id: "$run_id"},
    source_count: {$sum: 1},
    docs: {$push: {
      id: "$_id", status: "$status", event_count: "$event_count",
      started_at: "$started_at", updated_at: "$updated_at",
      completed_at: "$completed_at", metadata: "$metadata"
    }}
  }},
  {$match: {source_count: {$gt: 1}}},
  {$sort: {source_count: -1}}, {$limit: 200}
])
```

For each result, a completed/large source plus running/small source with near-adjacent `started_at` values supports API/worker split creation. A prior terminal/error source followed by a later running source with the same run supports retry. Metadata-only fields to compare are `status`, `event_count`, `started_at`, `updated_at`, `completed_at`, `agent_id`, `user_id`, and `metadata` (especially task/recovery/error markers).

**C. Cross-session or cross-run reuse:**

```javascript
db.traces.aggregate([
  {$match: {trace_id: {$exists: true, $ne: null}}},
  {$group: {
    _id: "$trace_id", source_count: {$sum: 1},
    sessions: {$addToSet: "$session_id"}, runs: {$addToSet: "$run_id"}
  }},
  {$match: {$expr: {$or: [
    {$gt: [{$size: "$sessions"}, 1]},
    {$gt: [{$size: "$runs"}, 1]}
  ]}}},
  {$sort: {source_count: -1}}, {$limit: 200}
])
```

Multiple sessions prove cross-session ID reuse; one session with multiple runs proves a run-identity conflict/reuse. A single session/run with many sources points away from cross-session propagation and toward duplicate create/retry/race.

**D. Metadata-only shape report for the "completed-large + running-one-token" signature:**

```javascript
db.traces.aggregate([
  {$match: {trace_id: {$exists: true, $ne: null}}},
  {$project: {
    trace_id: 1, session_id: 1, run_id: 1, _id: 1,
    status: 1, event_count: {$ifNull: ["$event_count", 0]},
    started_at: 1, updated_at: 1, completed_at: 1,
    agent_id: 1, user_id: 1, metadata: 1,
    has_events: {$gt: [{$size: {$ifNull: ["$events", []]}}, 0]}
  }},
  {$sort: {trace_id: 1, started_at: 1}}
])
```

Join this output to duplicate IDs from A (or add a `$group`/`$match` stage) and inspect whether the small running source has `event_count` 0/1, whether the large source has terminal timestamps, and whether metadata differs. Do not infer event identity from `event_count` alone: old `$slice` retention could make the retained array shorter than its logical count.

To list only groups containing both a completed and a running source (still metadata-only), use:

```javascript
db.traces.aggregate([
  {$match: {trace_id: {$exists: true, $ne: null}}},
  {$group: {
    _id: {trace_id: "$trace_id", session_id: "$session_id", run_id: "$run_id"},
    source_count: {$sum: 1},
    statuses: {$addToSet: "$status"},
    completed_counts: {$push: {$cond: [{$eq: ["$status", "completed"]}, {$ifNull: ["$event_count", 0]}, null]}},
    running_counts: {$push: {$cond: [{$eq: ["$status", "running"]}, {$ifNull: ["$event_count", 0]}, null]}},
    docs: {$push: {_id: "$_id", status: "$status", event_count: "$event_count", started_at: "$started_at", updated_at: "$updated_at", completed_at: "$completed_at", metadata: "$metadata"}}
  }},
  {$match: {$expr: {$and: [
    {$gt: ["$source_count", 1]},
    {$in: ["completed", "$statuses"]},
    {$in: ["running", "$statuses"]}
  ]}}},
  {$limit: 200}
])
```

Inspect `completed_counts` for the large value and `running_counts` for `1` (null entries are the other statuses). This identifies the shell signature without exposing `events.data`.

**E. Bulk/API-vs-worker hints without reading event payloads:**

```javascript
db.traces.aggregate([
  {$match: {trace_id: {$exists: true, $ne: null}}},
  {$group: {_id: "$trace_id", docs: {$push: {
    session_id: "$session_id", run_id: "$run_id", status: "$status",
    event_count: {$ifNull: ["$event_count", 0]}, started_at: "$started_at",
    updated_at: "$updated_at", completed_at: "$completed_at",
    agent_id: "$agent_id", user_id: "$user_id", metadata: "$metadata",
    has_metadata: {$gt: [{$size: {$objectToArray: {$ifNull: ["$metadata", {}]}}}, 0]}
  }}, source_count: {$sum: 1}}},
  {$match: {source_count: {$gt: 1}}},
  {$limit: 200}
])
```

Sparse sources (`agent_id`/`user_id` absent, empty metadata, event-rich) are compatible with the old bulk `$setOnInsert` shape, which set only session/run/status/started_at. A source with a user-message-only/very early timestamp next to a worker-complete source is compatible with API/worker immediate persistence. These are discriminators, not proof; old documents may legitimately have sparse optional fields.

**F. Migration dry-run (no writes):**

`python -m src.infra.session.trace_migration` defaults to dry-run. The plan reports each `(session_id, trace_id)` group's exact source IDs, `active`/`skip_reason`, source `event_count`, deterministic merged count, `source_document_count`, and global `index_preflight_clear`. It groups duplicate identity as `(session_id, trace_id)` (`src/infra/session/trace_migration.py:305-318`), while readiness remains a global `trace_id` assertion (`:379-382`). Use this output to see the running-one-token group without applying repair.

### 6. Interpretation of the reported failure

Proof from source/history: readiness now fail-closes when the duplicate preflight is non-empty, and no ordinary chat write should proceed until the unique index can be created (`src/infra/session/trace_storage.py:450-473`, `src/api/routes/health.py:163-168`). Proof from Git history: before `dd15687e`, both direct `insert_one` creates and bulk upserts could write without a uniqueness-ready gate, and index failures were non-fatal. Inference: the 424 groups are historical same-ID duplicate writes accumulated while the unique index was absent/failed, with API/worker immediate persistence the leading producer after March/May changes. Unanswered without metadata/log queries: exact mix of API/worker pairs, ARQ retries, and bulk races; source process identity is not stored in current trace documents.

## Caveats / Not Found

- No production MongoDB or logs were accessed; the proposed queries are read-only and must be run by an authorized operator.
- The startup preflight's 1,000-group cap means `duplicates=424` is a lower-bound-safe count only when the uncapped aggregation confirms fewer than 1,000 groups.
- `event_count` is a repairable projection and legacy arrays may have been `$slice`-truncated; use it with timestamps/status/metadata and migration checksums, not as proof of complete event history.
- A "running" source may be a genuinely live writer. Do not apply migration to such a group until the active writer is stopped/leased; the migration intentionally skips it by default.
- Current `create_trace` has a compatibility `TypeError` fallback to `insert_one` for test doubles/rolling wrappers (`src/infra/session/trace_storage.py:576-587`); production Motor supports `update_one(..., upsert=True)`, so this fallback is not evidence of a production collision by itself.
