# 上线说明（非破坏性）

## 结论

本次改动**不需要任何数据迁移**，直接拉镜像重启即可。已上线的 MongoDB 数据
一律保持原样，不做任何改写或删除。

## 数据层做了什么

| 集合 | 变化 | 兼容性 |
|------|------|--------|
| `analytics_daily_snapshot` | 新写入的行追加 `active_session_ids` / `new_session_ids` 数组 | 旧行没有这两个字段，读取时自动回退为原有整数语义（`_visible_metric`），不报错 |
| `analytics_daily_snapshot` | 每个已完整冻结的日期追加一行「完成标记」（`user_id = __snapshot_complete__`） | 标记行在所有聚合入口被排除；旧日期没有标记会被重新冻结一次以补齐历史缺口 |
| `analytics_backfill_state` | 追加 `failed_dates` 数组 | 缺失视为空列表 |
| `user_daily_activity` | 无结构变化 | — |
| `sessions` / `traces` | **完全不动** | — |

写入一律使用 `$setOnInsert` + `upsert`，已存在的快照行不会被覆盖。
索引只用 `create_index(background=True)` 幂等新增，没有 `drop_index`，
也没有把已有非唯一索引改成唯一。

## 回滚安全

新版本写入的数组字段是追加的，旧版本代码只读 `active_sessions` /
`new_sessions` 整数列，因此回滚到旧镜像不会崩溃，只是失去跨天去重能力
（回到旧行为）。完成标记行对旧版本而言是一行 `user_id` 不匹配任何真实用户的
文档，旧版本的聚合会把它当成一个 0 值分组，不影响既有数字。

## 灰度期间

- 所有新增 API 查询参数均为 Optional 且默认值等于旧行为，老前端不传时行为不变。
- 前端消费后端字段时有 `??` 兜底，后端未升级时不会崩。

## 上线后数字会变化的地方（预期内，属于修 bug）

1. **历史日期不再缩水**。这是本次的核心目标。
2. **活跃会话数可能变小**：此前跨天重复计数（同一会话两天有消息算 2），
   现在按会话去重算 1。这是修正，不是回退。
3. **会话数 KPI 主值从「新建会话」改为「活跃会话」**（PRD R4 要求），
   副行显示新建数；两个会话环图的中心与切片同步改为活跃会话口径。
4. **筛选后的环图数字会变**：此前三个环图完全忽略筛选参数（前端已在传、
   后端未声明），现在真正生效，因此筛选状态下的环图会与 KPI 卡对上。
5. **按角色筛选的数字可能变大**：此前从「区间内新建会话的用户」反推角色成员，
   漏掉了只使用旧会话的人，现在直接查 `users.roles`。
6. **by-persona 环图可能新增条目**：persona 归属统一为「会话 metadata 优先、
   缺失回退 trace metadata」（PRD 口径表），此前该端点只认会话 metadata。

## 首次启动行为

启动后台会依次跑：
- `AnalyticsBackfillWorker`（已有）：回填历史 activity 与快照，分批 + 幂等 +
  失败只记日志，不阻塞启动；失败日期记入 `failed_dates` 后续重试。
- `DailyFreezeWorker`（本次新增）：按 UTC+8 日界冻结「昨天」，堵住
  「00:00 后、首次查询前删数据」导致历史数字缩水的窗口。

两者都有 Redis 分布式锁，多副本部署安全。
