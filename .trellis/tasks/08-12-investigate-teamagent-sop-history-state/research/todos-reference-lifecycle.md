# Research: FastAgent/Search todo lifecycle and SOP delta

- Query: Trace FastAgent and Search native todo (`write_todos`) lifecycle, persistence, live/history replay, and reusable state/update correlation patterns for the TeamAgent SOP fix.
- Scope: mixed (internal code and focused fixture/tests)
- Date: 2026-08-12

## Findings

### FastAgent/Search source of truth

- Both agents use the shared deep-agent event processor rather than implementing todo state themselves. Their graph wrappers explicitly leave the outer graph without a checkpointer while the inner deep-agent checkpointer persists conversation state: [src/agents/fast_agent/graph.py:101-110] and [src/agents/search_agent/graph.py:108-117]. The native `TodoListMiddleware` remains enabled in the default Fast/Search harness profile (`todo_enabled=True`): [src/agents/core/harness_prompt_overrides.py:270-282] and [tests/agents/test_team_harness_profile.py:44-50].
- LangChain `on_tool_start` for `write_todos` is special-cased by `ToolEventMixin`: it extracts `data.input.todos`, and when the list is non-empty emits `presenter.present_todo(...)` with current depth/agent id; it does not emit `tool:start`: [src/infra/agent/events/tool_events.py:84-112]. `on_tool_end` for `write_todos` is ignored, so the start-side input is the complete update payload: [src/infra/agent/events/tool_events.py:114-122].
- `present_todo` creates a `todo:updated` event containing the full `todos` list plus timestamp, depth, and agent identity via `_build_event`: [src/infra/writer/presenter_events.py:230-250], [src/infra/writer/presenter_events.py:83-109]. Items use `content`, optional `activeForm`, and status `pending | in_progress | completed`; frontend event types mirror this shape: [frontend/src/hooks/useAgent/types.ts:116-124], [frontend/src/hooks/useAgent/types.ts:192-205].

### Persistence and update semantics

- Todo updates are ordinary presenter events. `Presenter.emit` routes each event through `save_event`; storage writes the event type/data to `DualEventWriter.write_event` with session id, trace id, agent id, and run id: [src/infra/writer/presenter_storage.py:160-205]. There is no separate todo collection or upsert path. Therefore the durable source of truth for a session replay is the ordered `todo:updated` event stream (while the active model/checkpointer also sees the native middleware state).
- Each `write_todos` call is a full snapshot replacement, not a patch. Top-level live processing uses `upsertTodoPart`: replace the existing `todo` message part or append one: [frontend/src/hooks/useAgent/eventProcessor.ts:368-386], [frontend/src/hooks/useAgent/eventProcessor.ts:499-508]. Nested subagent parts apply the same replacement rule, one todo part per subagent: [frontend/src/hooks/useAgent/messageParts.ts:193-202]. No event id, plan id, or item id is used for correlation; ordering plus depth/agent id determines which snapshot wins.
- At stream completion/history cleanup, `clearAllLoadingStates` preserves completed/pending items but converts any `in_progress` item to `pending`, clears `activeForm`, and marks the todo part non-streaming: [frontend/src/hooks/useAgent/messageParts.ts:612-659]. This means an interrupted live run is intentionally represented as pending in the UI rather than falsely completed.

### Live and history behavior

- Live SSE `todo:updated` events are included in the message-transforming event allowlist and sent to `processMessageEvent`; top-level and nested depth routing is shared with history: [frontend/src/hooks/useAgent/eventHandlers.ts:307-323], [frontend/src/hooks/useAgent/eventProcessor.ts:370-386]. The event handler rejects stale SSE events older than the loaded history timestamp before applying them: [frontend/src/hooks/useAgent/eventHandlers.ts:76-96].
- History reconstruction does not special-case `todo:updated`; `processHistoryEvent` creates/locates the assistant message and delegates every content event (including todo) to `processMessageEvent` with `isStreaming=false`: [frontend/src/hooks/useAgent/historyLoader.ts:141-175], [frontend/src/hooks/useAgent/historyLoader.ts:218-266]. Thus all stored snapshots are replayed in server-provided global order (`history_order`, then legacy seq/timestamp fallback): [frontend/src/hooks/useAgent/historyLoader.ts:50-109], [frontend/src/hooks/useAgent/historyLoader.ts:300-320]. The last snapshot for a given message/depth replaces prior snapshots.
- Focused fixtures codify the contract: `tests/events/stream_events.json:181-199` contains a `todo:updated` full list, and `tests/events/langchain_stream_events.json:96-143` states `write_todos` emits `todo:updated` only, never tool start/result. Existing frontend tests cover the reducer’s replacement behavior indirectly via `eventProcessor`/history loader fixtures; no separate backend todo store exists.

### SOP interface and precise delta

- TeamAgent removes `TodoListMiddleware`/`write_todos` from the model request and uses `update_sop` as the formal replacement: [src/agents/team_agent/harness_profile.py:1-10], [src/agents/team_agent/nodes.py:600-614], [src/agents/team_agent/tool_exclusion.py:80-87].
- SOP has a durable Mongo source of truth independent of message/checkpointer state: `SopRunStore` uses a unique `(session_id, team_id)` document, full `upsert_plan` snapshots, and locked step/status updates returning a complete snapshot: [src/agents/team_agent/sop/store.py:23-31], [src/agents/team_agent/sop/store.py:80-104], [src/agents/team_agent/sop/store.py:106-164]. Plan identity is `plan_id`; updates are keyed by `(session_id, team_id)` and step id, with explicit plan status and output/error fields.
- Every accepted SOP mutation emits a full `sop:updated` snapshot through `Presenter.emit_team_event`, so it is also durably present in session history: [src/agents/team_agent/sop/tool.py:45-51], [src/agents/team_agent/sop/tool.py:82-107]. Creation with dispatch steps also emits `approval_required` (type `sop_plan`) and blocks on `wait_for_response`; approval/rejection/timeout transitions emit further snapshots: [src/agents/team_agent/sop/tool.py:110-163]. Validation failures intentionally write neither store nor event: [src/agents/team_agent/sop/tool.py:184-224].
- Frontend SOP state is deliberately outside message parts. Live handlers reduce `approval_required(sop_plan)` and `sop:updated` into a dedicated `sopPlan` state with full-snapshot replacement and approval-id preservation by matching `plan_id`: [frontend/src/hooks/useAgent/eventHandlers.ts:258-283], [frontend/src/types/sop.ts:225-252]. History loader skips SOP events during message reconstruction: [frontend/src/hooks/useAgent/historyLoader.ts:165-175]. `useAgent.loadHistory` separately orders replayable `sop:updated`/SOP approvals, chooses the latest snapshot, and only attaches an approval from the same plan id: [frontend/src/hooks/useAgent.ts:480-514].

| Concern | Fast/Search native todos | TeamAgent SOP | Fix-design implication |
|---|---|---|---|
| Durable source | Ordered session trace events (`todo:updated`); no dedicated collection | Mongo `sop_runs` current snapshot plus ordered `sop:updated`/approval events | SOP already has a stronger durable source; history should reconcile event replay with store identity, not treat message parts as source |
| Update shape | Full list replacement; implicit correlation by message + depth/agent + event order | Full plan replacement; explicit `(session, team, plan_id)` and step ids | Preserve full-snapshot semantics, but enforce plan-id correlation on every replay/update |
| Live UI | Todo is a `MessagePart`; latest event replaces prior part | SOP is dedicated `sopPlan` state; excluded from messages | Keep SOP out of assistant bubbles; do not copy todo part behavior blindly |
| History UI | Generic history reducer replays every `todo:updated`; last snapshot wins | Dedicated replay selects latest SOP snapshot and same-plan approval; message loader skips SOP events | SOP hydration must use one ordering function and same-plan filtering; stale approval/event must not overwrite current plan |
| Terminal cleanup | `in_progress` -> `pending` on clear/interruption | Explicit plan/step terminal statuses (`completed`, `failed`, `cancelled`, `timed_out`, etc.) persisted and replayed | Avoid converting SOP `running` to pending during generic message cleanup; terminal state comes from store/event |
| Correlation | `depth` + `agent_id` only; no per-item IDs | `plan_id`, `step_id`, session/team key, approval id | Any SOP fix should carry plan identity through event, store, and frontend reducer; preserve approval id only for matching plan |

## Caveats / Not Found

- No FastAgent/Search-specific todo persistence adapter or API endpoint was found; the only durable path is generic trace/session event storage. The inner LangGraph checkpointer is described as persisting conversation history, but the UI’s durable todo replay is based on `todo:updated` trace events.
- `todo:updated` history replay assumes the backend page contains all relevant snapshots and has stable ordering. Unlike SOP, there is no dedicated “latest todo snapshot” extraction outside message reconstruction.
- Existing focused fixtures document event routing, but there is no test asserting cross-page todo snapshot reconciliation or stale-event protection beyond the generic history timestamp gate.
- SOP history ordering in `useAgent.ts` uses timestamp then `seq`/array index locally, while generic message reconstruction prefers `history_order`; this is a potential ordering consistency gap when SOP events interleave across traces.
