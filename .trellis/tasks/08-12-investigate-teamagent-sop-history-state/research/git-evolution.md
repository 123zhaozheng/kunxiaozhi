# Research: Git evolution of TeamAgent SOP/history state

- Query: Identify commits that introduced or changed SOP DAG/update/history contracts, comparable todo persistence, and history ordering; determine whether stale SOP hydration is a regression or incomplete parity port.
- Scope: internal Git history, blame, diffs, and tests
- Date: 2026-08-12

## Findings

### Chronology and contracts

- `9c99d480` (2026-08-03, `feat(team): add approved TeamAgent orchestration harness`) first introduced the older TeamPlan contract. The frontend history path folded `approval_required`, `team:plan`, `team:step`, and `team:run` events through `normalizeTeamPlanEvent` + `reduceTeamPlan` in chronological event order ([frontend/src/hooks/useAgent.ts, commit diff around lines 451-477]; [frontend/src/types/teamPlan.ts]). The reducer was deliberately incremental: plan/step events merged fields into the current state instead of replacing it. History also excluded these events from message bodies and skipped team-plan approvals in the generic approval list ([frontend/src/hooks/useAgent/historyLoader.ts, commit diff around lines 62-143]).
- `eca662a2` (2026-08-03, immediate revert) removed that orchestration harness, its TeamPlan UI/types, backend orchestration, tests, and history handling. This is relevant provenance: the later SOP implementation was a fresh replacement, not a small rename of a continuously maintained TeamPlan path.
- `75a92f4d` (2026-08-10, `feat(team): 完成审批门禁 SOP DAG 后端`) introduced the current SOP backend. `SopRunStore` persists one full `SOPPlan` by `(session_id, team_id)`, updates steps/status under a lock, and returns complete snapshots (`src/agents/team_agent/sop/store.py:23-31,80-164`). `update_sop` emits full `sop:updated` snapshots; initial plans with dispatch steps additionally emit `approval_required` containing `id`, `plan_id`, `type: sop_plan`, and a nested full plan snapshot, then block for approval (`src/agents/team_agent/sop/tool.py:45-76,110-163`). Confirmed mutations emit a new full snapshot; terminal transitions (`running`, `completed`, `failed`, `cancelled`, `timed_out`, `rejected`) are persisted/emitted. This establishes replacement semantics for SOP snapshots, unlike the reverted TeamPlan merge reducer.
- `04612bf2` (2026-08-10, `feat(frontend): 完成 SOP DAG 可视化与历史恢复`) added `SopPlan`, `normalizeSopEvent`, and `reduceSop`. The reducer documentation explicitly says full snapshot replacement, with only same-plan `approval_id` carry-forward (`frontend/src/types/sop.ts:224-252`). Live handlers apply exactly one reducer call per SSE event: approval events and `sop:updated` both update dedicated `sopPlan` state and never enter assistant message parts (`frontend/src/hooks/useAgent/eventHandlers.ts:258-283`; `frontend/src/hooks/useAgent/historyLoader.ts:115-195`).
- The same `04612bf2` commit added a separate `useAgent.loadHistory` SOP pass. It sorts events by timestamp, then `seq`/array index, selects the last replayable SOP event as the plan, then searches backward for any same-plan `approval_required` and calls `reduceSop(restoredPlan, latestApproval)` (`frontend/src/hooks/useAgent.ts:480-514`, all lines blamed to `04612bf2`). Because the approval envelope contains an old full snapshot (normally `awaiting_confirmation` with pending steps), this second reducer call can replace a later `completed`/`running` snapshot. This is the likely regression point: the implementation copied the old TeamPlan idea of restoring approval metadata but retained full nested approval data while using a replacement reducer.
- `0b968f6b` (2026-08-11, `fix(history): 恢复完整会话历史加载`) corrected the history query from `currentRunId` to `targetRunId` so normal session history is not accidentally narrowed (`frontend/src/hooks/useAgent.ts:387-393`). This broadens the event set seen by SOP hydration and makes same-session multi-run/replan collisions more likely to surface; it did not change the SOP reducer or its approval reapplication.
- `1795fac0` (2026-08-07, `fix(history): 修正混合事件重建与分页边界`) changed generic message reconstruction ordering from timestamp-only to a stable `seq`/legacy bucket plus timestamp/trace/event identity comparator (`frontend/src/hooks/useAgent/historyLoader.ts`, commit diff). It did not update the SOP-specific timestamp sort added later in `04612bf2`; thus SOP and message history already had different ordering contracts.
- `a80af817` (2026-08-07, `feat(history): 完成会话历史游标分页与纯读取链路`) introduced `getAllEvents`, cursor pagination, deduplication, and `history_complete/history_error` diagnostics. SOP hydration consumes the accumulated pages but has no special handling for an incomplete page; a missing terminal `sop:updated` can leave a partial/old plan. The UI exposes diagnostics, but does not reconcile SOP state from `SopRunStore`.
- `b09e34be` (2026-08-11, `fix(history): 修复合并事件历史重放顺序`) added server-provided `history_order` v3 tuples and made the generic `historyLoader` comparator use the full tuple when present (`frontend/src/hooks/useAgent/historyLoader.ts:59-113`; `src/infra/session/history_cursor.py:11-150`). The SOP-specific `orderedHistoryEvents` comparator in `useAgent.ts:484-491` still ignores `history_order`, so merged/legacy pages can select a different “latest” SOP event than the message replay. This is an independent ordering/parity gap, though the approval overwrite alone reproduces stale status.

### Comparable todo behavior and parity assessment

- Native FastAgent/Search todos predate SOP and remain ordinary full-snapshot `todo:updated` presenter events (`src/infra/agent/events/tool_events.py:84-122`; `src/infra/writer/presenter_events.py:230-250`). History sends them through the same ordered `processMessageEvent` fold as live events; `upsertTodoPart` replaces the prior todo part (`frontend/src/hooks/useAgent/eventProcessor.ts:368-386,499-508`). There is no separate history pass that re-applies an earlier approval/tool envelope. This gives todos one chronological reducer and “last snapshot wins” semantics.
- SOP intentionally replaces `write_todos` in team mode (`src/agents/team_agent/harness_profile.py:1-10`; `src/agents/team_agent/nodes.py:600-614`), but the port is not behaviorally complete: SOP has a dedicated state and durable Mongo snapshot, while history adds a second reducer pass for approval metadata. The old TeamPlan reducer merged incremental events; the new SOP reducer replaces full snapshots. Reusing the old “restore latest plan plus approval” shape without extracting only the approval id is an incomplete parity port, not evidence that backend persisted stale state.

### Regression/backward-compatibility implications

- Evidence supports a frontend-only regression introduced by `04612bf2`; no later commit changed backend SOP snapshot semantics. Live SSE remains correct because events are reduced once in arrival order and a later `sop:updated` replaces status/steps while preserving only same-plan approval id.
- Existing persisted histories remain backward-compatible at the event-schema level: `sop:updated` and `approval_required(sop_plan)` are full snapshots and can still be normalized. However, old histories containing both events are rendered stale by the current history pass, especially after `0b968f6b` restored session-wide history. Fixing hydration should retain the latest selected plan and copy only matching approval envelope metadata; it should not feed the nested approval plan back through `reduceSop`.
- History pagination/ordering changes add residual risk: incomplete pages may omit terminal snapshots, and `history_order` is honored by generic replay but not SOP selection. A robust compatibility fix should use the shared ordering comparator (or server ordering) and surface incomplete-history caveats rather than treating an approval snapshot as authoritative over a later plan snapshot.

## Caveats / Not Found

- No commit after `04612bf2` adds a `useAgent.loadHistory` regression test for approval-before-completed or approval-after-completed SOP events. Existing tests cover `reduceSop`, live handlers, message exclusion, and pagination, but not the callback’s final `sopPlan` state.
- `SopRunStore` is a current-plan store keyed by session/team, not a historical query API; the frontend currently reconstructs from events and does not read that store. The backend therefore cannot independently correct a truncated event page in the current architecture.
- Commit dates are author dates from local Git history; all referenced hashes were inspected read-only.
