# Research: TeamAgent Handoff Contract

- Query: DeepAgents 0.6.7 task-tool semantics, event correlation, role roster determinism, checkpointer ownership, and failure/retry/cancellation behavior for a structured TeamAgent SOP handoff.
- Scope: mixed (repository code plus locked local dependency source)
- Date: 2026-08-03

## Findings

### DeepAgents task contract

- The lock pins `deepagents==0.6.7` (`uv.lock:954-967`) and the installed package reports `0.6.7`.
- `TaskToolSchema` has only two model-visible inputs: free-form `description` and `subagent_type` (`.venv/Lib/site-packages/deepagents/middleware/subagents.py:267-278`). A machine-readable handoff therefore needs either a JSON envelope inside `description` (validated by application code) or a replacement/wrapper tool; the stock `task` schema has no objective/context/artifact/correlation fields.
- `_build_task_tool` validates `subagent_type`, requires a runtime `tool_call_id`, copies parent state excluding `messages`, todos, structured response, and skill-private keys, and invokes the selected runnable with a single `HumanMessage(description)` (`.../subagents.py:533-539`, `564-586`, `588-609`). Unknown role names return an error string rather than raising (`569-571`, `593-595`), so callers should validate roster membership before a call.
- A completed subagent must return `messages`; otherwise a `ValueError` is raised (`493-501`). If `structured_response` exists it is JSON serialized into the parent `ToolMessage`; otherwise the last non-empty `AIMessage` text is selected (`503-529`). This supports a Pydantic/TypedDict `response_format` for machine-readable role results (`.../subagents.py:115-153`, `172-176`), but not structured task input without a custom tool/schema.
- Exceptions from `subagent.invoke/ainvoke` are not caught by the task wrapper (`584-586`, `607-609`), so they surface as tool errors and abort the parent model turn unless an outer orchestration layer catches/records them. The app's retry middleware retries model calls (429/5xx/timeouts/empty/truncated output) only; it does not retry a failed task invocation (`src/infra/agent/middleware/retry.py:29-88`, `167-239`, `280-311`).
- `SubAgentMiddleware` preserves declared order in `_get_subagents()` and exposes a `frozenset` of names (`.../subagents.py:690-710`, `712-766`). Its task tool description is rendered once from `name: description` pairs; `{available_agents}` is substituted only when present (`480-491`).

### Roster construction and determinism

- `TeamAgent` iterates `team.active_members` directly when creating role specs (`src/agents/team_agent/nodes.py:398-455`). `TeamResponse.active_members` only filters `enabled`; it does not sort by `position` (`src/kernel/schemas/team.py:143-145`). Mongo conversion and updates preserve the stored member list order (`src/infra/team/storage.py:150-165`, `445-452`), so deterministic ordering requires an explicit sort/tie-breaker in the runtime roster compiler if order is part of the contract.
- `build_team_member_subagent_type` derives `team-{member_id}-{role_slug}` (`src/agents/team_agent/prompt.py:157-164`). Duplicate member IDs/role slugs can collide; DeepAgents' graph dict comprehension keeps the last runnable for a duplicate name (`.venv/Lib/site-packages/deepagents/middleware/subagents.py:480-483`). Validate uniqueness before compilation.
- DeepAgents automatically inserts a `general-purpose` subagent at index 0 whenever no explicit spec has that name, unless the active harness profile disables it (`.venv/Lib/site-packages/deepagents/graph.py:652-709`; documented at `330-381`). Current TeamAgent supplies only role specs for an explicit team (`nodes.py:398-455`), so the effective `task` roster silently includes `general-purpose`; the local fallback at `464-487` does not prevent this in team mode. Either pass a deliberate policy/profile or include/test an explicit general-purpose entry.
- The router's default role is selected from `default_member_id` or the first active member (`nodes.py:236-253`). This also depends on list order and should be captured in the compiled roster/SOP rather than recomputed after confirmation.

### Event correlation and observability

- DeepAgents tags nested task runs with `ls_agent_type=subagent` and forwards only callbacks, tags, and configurable values to the child (`.../subagents.py:442-463`, `541-562`, `577-585`). The task runtime's `tool_call_id` is available to the tool but is not included in the app's `agent:call` payload by default.
- `AgentEventProcessor` treats `on_tool_start/end/error` for tool name `task` specially (`src/infra/agent/events/processor.py:213-225`). Start maps `subagent_type`, description, event `run_id`, and `checkpoint_ns` to an instance ID (`src/infra/agent/events/subagents.py:62-105`); end/error resolves by `checkpoint_ns` and emits `agent:result` with success/error (`117-173`). The emitted presenter events currently carry agent ID/depth but no team ID, member ID, persona preset/version, SOP step, or handoff correlation ID (`src/infra/writer/presenter_events.py:253-312`).
- If `checkpoint_ns` is empty, the mixin stores the mapping under `""`; concurrent tasks can overwrite that key (`subagents.py:71-88`). A structured handoff should carry a unique `team_run_id`/`handoff_id`/`step_id` and event persistence should prefer those over inferred namespace suffixes.
- Generic tool events use event `run_id` as a synthetic tool-call ID (`src/infra/agent/events/tool_events.py:58-60`) and preserve it through presenter `tool:start/result` (`80-111`, `148-159`), which is a reusable pattern for emitting task correlation IDs.

### State and checkpoint ownership

- The outer TeamAgent graph is intentionally compiled with `checkpointer=None`; comments say only the inner DeepAgent checkpointer persists conversation state (`src/agents/team_agent/graph.py:94-107`). The inner graph receives a per-session checkpointer from `get_async_checkpointer(thread_id=session_id)` (`src/agents/team_agent/nodes.py:344-348`) and invokes it with the same `thread_id` (`542-552`, `556-570`). Do not add a second checkpointer sharing the same namespace; use an isolated namespace/thread if the outer graph gains resumable SOP nodes.
- Persistent backend selection is PostgreSQL/MongoDB, with thread-scoped `MemorySaver` fallback that is lost on restart (`src/infra/storage/checkpoint.py:288-356`). Confirmation/SOP state must therefore be in the durable checkpointer or application persistence, not only in process memory.
- `TeamAgentState` currently contains only `input`, `session_id`, `messages`, `output`, and `attachments` (`src/agents/team_agent/state.py:6-12`). The inner invocation actually passes `build_goal_input(...)` containing only `messages` (plus optional rubric) (`src/infra/goal.py:95-106`); attachment data is converted into the `HumanMessage` text/multimodal content (`src/agents/core/node_utils.py:278-324`). A stable attachment manifest and plan/approval status therefore need explicit state/config fields or durable metadata; relying on the outer `attachments` field will not make it part of the inner checkpointed state.

### Confirmation, resume, cancellation, and failure

- LangGraph's native `interrupt(value)` pauses a node, surfaces a resumable value, and resumes with `Command(resume=...)`; it requires a checkpointer and re-executes the node from its beginning (`.venv/Lib/site-packages/langgraph/types.py:800-820`, `811-817`, `822-879`). Any plan node must be side-effect free/idempotent before the interrupt, otherwise resume can duplicate work. This is the cleanest way to enforce “plan emitted, no task call, explicit confirm, then dispatch.”
- DeepAgents can attach `HumanInTheLoopMiddleware` via `interrupt_on`, but the current TeamAgent call does not pass `interrupt_on` (`nodes.py:542-552`). Per-subagent `interrupt_on` only gates tools inside that child (`.../subagents.py:631-649`, `745-747`); it does not create a single router-level approval boundary before the first `task` call.
- Existing app-level human approval is durable/distributed: `AskHumanTool` creates an approval, emits `approval_required`, waits for a response, and returns `success`, `rejected`, or `timeout` JSON (`src/infra/tool/human_tool/tool.py:156-209`, `311-360`; routes `src/api/routes/human.py:103-209`, `245-283`). It can support confirmation UX, but a router must persist SOP/approval identity and stop before invoking `task`; a prompt-only ask is not a gate.
- TeamAgent cancellation propagates `CancelledError`/`TaskInterruptedError` to the inner graph task and cancels it (`src/agents/team_agent/graph.py:194-221`). The general streaming wrapper checks interrupts between events and on one-second timeouts, drains queued events, cancels the stream task, flushes, and emits terminal events (`src/agents/core/base.py:416-439`, `485-533`). TeamAgent's node directly uses `inner_graph.astream_events` and must preserve equivalent terminal/error handling when adding per-role orchestration.
- Application task lifecycle supports `queued/pending/starting/running/cancelling/cancelled/completed/failed/recovering/expired` (`src/infra/task/status.py:9-20`). Recovery refuses completed or explicitly cancelled runs and otherwise resumes from the current run/checkpoint (`src/infra/task/recovery.py:443-496`). A TeamAgent result must not be marked completed when required handoffs are missing; persist partial role results and mark recoverable failure before retry/resume.

## Recommended contract shape

1. Compile a deterministic, validated roster once (sorted `position`, then `member_id`; reject duplicate generated names) and persist the selected member/persona snapshot/version in the SOP.
2. Represent each handoff as an application schema with `handoff_id`, `team_run_id`, `sop_step_id`, `subagent_type`, `objective`, `context`, `attachment_manifest` (verified sandbox paths), `predecessor_artifacts`, `expected_artifacts`, and `attempt`. Embed it in the task description only as a compatibility bridge, or replace/wrap the task tool with a schema that validates it before invocation.
3. Use a Pydantic `response_format` for role results so the returned `ToolMessage` is machine-readable; validate required artifacts and correlation IDs before synthesis.
4. Add a dedicated plan/approval checkpoint boundary using LangGraph `interrupt` (or the existing durable approval service plus an explicit resume command). Never call the stock task tool before an approved SOP state is present.
5. Emit/persist the handoff IDs on plan, approval, task start/progress/result/error, retry, cancellation, synthesis, and terminal events; do not rely solely on inferred `checkpoint_ns` mappings.

## Caveats / Not Found

- No existing TeamAgent SOP/plan schema, attachment-to-sandbox materializer, or router-level confirmation state was found. Current sandbox support only registers `upload_url_to_sandbox` as an on-demand tool (`src/agents/search_agent/context.py:228-233`; implementation `src/infra/tool/upload_url_tool.py:97-205`), so prompt text does not guarantee pre-dispatch materialization.
- DeepAgents 0.6.7 has no built-in structured handoff envelope or role-level retry/cancellation protocol for synchronous `task`; those behaviors must be implemented in application middleware/state. The separate async-subagent middleware has launch/check/update/cancel statuses, but it is a remote `graph_id` path and is not what TeamAgent currently configures (`.venv/Lib/site-packages/deepagents/middleware/async_subagents.py:57-87`, `608-679`, `866-899`).
- Dependency source was inspected from the locked local virtual environment; no external API behavior beyond the pinned source was assumed.
