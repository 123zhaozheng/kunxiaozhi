# Research: Team Persona Search-Only Member Gate

- Query: Trace Team creation/editing and runtime member-mode flow; determine how a selected Persona's Fast/Search mode is represented, validated, persisted, and instantiated under the Team harness/DAG, including Team chat selection requirements.
- Scope: mixed (repository-only; no external dependency research was needed)
- Date: 2026-08-10

## Findings

### End-to-end data flow

1. Persona capability mode is currently an identity-level field, not a Team-member field.
   `src/kernel/schemas/persona_preset.py:11-13` defines `PreferredAgentId` as `Literal["fast", "search"]`, with default `fast`. The full preset, update/create contracts, and runtime snapshot expose `preferred_agent_id` at `src/kernel/schemas/persona_preset.py:95-109`, `:135-149`, `:166-196`, and `:199-212`.
   `src/agents/core/persona.py:29-43` resolves a persona-bound chat to the valid preferred mode, then requested mode, then `fast`.

2. Team member payloads contain only the referenced Persona ID plus role presentation/instructions. `src/kernel/schemas/team.py:21-56` (`TeamMemberCreate`, `TeamMemberUpdate`, `TeamMemberResponse`) has no mode field. Team create/update carry lists of those members at `src/kernel/schemas/team.py:59-101`.
   Frontend mirrors this exactly: `frontend/src/types/team.ts:4-13` has no mode, and create/update requests at `frontend/src/types/team.ts:34-65` send only `persona_preset_id` and role metadata.

3. Team builder currently offers every visible Persona as a role candidate. `frontend/src/components/team/TeamBuilder.tsx:153-163` fetches `personaPresetApi.list({ limit: 100 })`; `frontend/src/components/team/TeamBuilder.tsx:350-359` filters only by search text; and `frontend/src/components/team/TeamBuilder.tsx:694-738` renders every `filteredPresets` item as selectable. `handleAddRole` copies only ID/name/avatar/tags into a `TeamMember` at `frontend/src/components/team/TeamBuilder.tsx:205-220`. No `preferred_agent_id` filter or display is present.
   On save, `frontend/src/components/team/TeamBuilder.tsx:253-278` serializes members without mode and calls `teamApi.create` or `teamApi.update`. `frontend/src/services/api/team.ts:105-139` posts those typed bodies to `/api/teams` and `/api/teams/{id}`.

4. Backend Team CRUD accepts and persists member IDs/metadata without resolving Persona mode. `src/api/routes/team.py:47-79` passes Pydantic `TeamCreate`/`TeamUpdate` directly to `TeamManager`. `src/infra/team/manager.py:62-83` forwards member `model_dump` data on create; `src/infra/team/manager.py:140-159` forwards update data. `src/infra/team/storage.py:88-100` persists only the member fields shown in the schema, `src/infra/team/storage.py:126-128` bounds the list, and `src/infra/team/storage.py:303-338` / `:430-471` writes create/update documents. There is no `preferred_agent_id` in the stored Team member document or API response conversion (`src/infra/team/storage.py:151-177`).

5. Team manager validation currently checks only active status and Persona existence at runtime. `src/infra/team/manager.py:192-216` calls raw Persona storage `get_by_id` and drops missing presets; it never checks `preferred_agent_id`. `src/infra/team/manager.py:218-234` returns a Team only when it has active members and at least one existing Persona. Consequently, a Fast Persona can be saved into a Team and remains valid for runtime resolution.
   `PersonaPresetManager` itself enforces only the existing skill/mode contract (`src/infra/persona_preset/manager.py:58-62`, plus create/update calls at `:143-171` and `:273-306`), which means a no-skill Fast preset is valid and is the case relevant to this Team gate.

6. Runtime path is an outer one-node Team graph plus a per-request DeepAgents inner graph. `src/agents/team_agent/graph.py:80-108` builds `START -> team_router_node -> END`; `src/agents/team_agent/graph.py:137-180` places `team_id` in TeamAgent context/config. `src/agents/team_agent/nodes.py:95-126` resolves an explicit Team through `TeamManager.resolve_team_for_runtime`, rejecting not-found/no-active-member teams, while no `team_id` deliberately returns `None` for fallback.
   For a resolved Team, `src/agents/team_agent/nodes.py:213-238` calls `PersonaPresetManager.use_preset` for each active member and injects only `system_prompt`/selected skills into role prompt sections. `src/agents/team_agent/nodes.py:430-494` creates one custom DeepAgents subagent per active Team member, all with the same `role_tools`; `src/agents/team_agent/nodes.py:613-626` assembles the Team inner graph with `create_deep_agent` under the Team harness profile. No member's `preferred_agent_id` is read, and no independent Fast/Search graph is instantiated for a member. Team harness behavior is shared and intentionally excludes native Todo via `src/agents/team_agent/harness_profile.py:19-44`.
   The role prompt/subagent identity is derived from Team role metadata only: `src/agents/team_agent/prompt.py:24-40` builds the router roster and `src/agents/team_agent/prompt.py:74-99` maps `member_id`/`role_name` to the DeepAgents `task` subagent type.

7. Chat mode and Team selection are separate frontend state. `frontend/src/hooks/useAgent.ts:70-82` tracks `currentAgent` and `selectedTeamId`; `frontend/src/hooks/useAgent.ts:676-691` submits `selectedTeamId` only when `currentAgent === "team"`; `frontend/src/hooks/useAgent.ts:739-753` / `:786-801` stores `team_id` in optimistic session metadata only when a Team is selected; and `frontend/src/hooks/useAgent.ts:945-961` changes these values independently. Existing regression tests lock this behavior in `frontend/src/hooks/useAgent/__tests__/teamRequestScoping.test.ts:10-21`.
   `frontend/src/components/chat/ChatInputSelectors.tsx:182-203` mounts `TeamPickerModal` when Team mode is active. `frontend/src/components/team/TeamPickerModal.tsx:33-41` loads `/api/teams`; `frontend/src/components/team/TeamPickerModal.tsx:61-75` filters the list; `frontend/src/components/team/TeamPickerModal.tsx:77-93` selects/clears IDs; and `frontend/src/components/team/TeamPickerModal.tsx:209-217` shows a no-team message but does not itself invoke creation. The modal does expose direct creation/manage actions at `frontend/src/components/team/TeamPickerModal.tsx:142-188`.
   The welcome surface already distinguishes unselected Team mode: `frontend/src/components/chat/WelcomePage.tsx:294-316` shows Team cards/starter state only when `currentAgent === "team"` and `!selectedTeamId`; `:322-324` exposes a change-Team action after selection. However, the actual send callback remains callable with no Team ID.

8. Backend chat validation currently preserves the old fallback contract. `src/api/routes/chat_validation.py:6-15` only strips persona/enabled skills when `agent_id == "team" and request.team_id`; with no `team_id` it does nothing. The route calls persona resolution, model validation, and this helper at `src/api/routes/chat.py:397-422`, then queues/submits the request with `team_id` unchanged at `src/api/routes/chat.py:552-598`. Existing tests explicitly require the old behavior: `tests/api/routes/test_chat_team_validation.py:8-18` permits missing Team ID and `tests/api/routes/test_chat_team_validation.py:56-68` permits a Persona fallback. Runtime tests also assert `resolve_runtime_team(team_id=None)` returns `None` (`tests/unit/agents/test_team_router.py:188-200`).

### Minimum enforcement points

- Authoritative Team member mode gate: validate referenced Persona presets in `TeamManager.create_team` and `update_team` before calling storage, or in a shared manager helper called by both. Resolve each referenced preset in the current owner/admin visibility scope and reject any member whose preset `preferred_agent_id != "search"`; this covers REST UI saves and the LLM `create_agent_team` tool because that tool delegates to `TeamManager` (`src/infra/tool/team_tool.py:273-317`). The manager is the smallest common write boundary; storage cannot reliably enforce owner-scoped Persona visibility and does not currently receive `owner_user_id` for Persona lookups.
- Runtime fail-closed gate: extend `TeamManager.validate_team_members` / `resolve_team_for_runtime` to inspect the resolved Persona's `preferred_agent_id` and omit or reject non-Search members. Prefer rejecting the Team as unavailable rather than silently changing the Persona's mode, so runtime cannot execute a previously saved Fast member. This is needed even after write validation because runtime reads existing stored documents directly and `use_preset` can later resolve changed Persona data.
- Runtime mode behavior: after the gate, no Team-specific member mode field or separate member graph is needed. Existing Team assembly is already the Team harness/DAG; every accepted member should be treated as Search-capable through the shared Team role tool surface. Do not route members through `resolve_persona_agent_id` to instantiate Fast/Search outer agents: the Team graph intentionally creates role subagents under one Team harness (`src/agents/team_agent/nodes.py:430-494`, `:613-626`).
- UI candidate gate: filter TeamBuilder's fetched presets to `preferred_agent_id === "search"` before search filtering and role rendering (`frontend/src/components/team/TeamBuilder.tsx:350-359`, `:722-738`). This removes Fast from the selectable list, but must remain a usability guard only; REST/LLM/runtime checks remain authoritative.
- Team chat selection gate: on the frontend, block send while `currentAgent === "team" && !selectedTeamId` and keep the Team picker/create affordance visible. On the backend, change `validate_team_agent_request` to reject Team requests lacking `team_id` (and retain the existing explicit-Team stripping behavior). This is the minimum cross-client guarantee because direct API/task submissions bypass the UI.
- Available Team definition: the current runtime definition is an owned Team with at least one active member whose Persona exists (`src/infra/team/manager.py:218-234`). The picker and welcome list currently include empty/no-active Teams (`frontend/src/components/team/TeamPickerModal.tsx:220-225` counts but does not filter; `TeamBuilderWrapper` list uses normal Team API), so either filter those from selectable cards or surface a recoverable unavailable-team error. The backend gate remains necessary for race/deletion cases.

### Affected tests and recommended coverage

- Backend Team write/runtime: extend `tests/unit/infra/test_team_manager.py:153-248` with Search-accepted and Fast-rejected create/update/runtime cases; add owner/visibility or missing-Persona cases as appropriate.
- Backend Team chat gate: update `tests/api/routes/test_chat_team_validation.py:8-18` to require a missing-Team error and retain explicit-Team persona stripping tests. Update `tests/unit/agents/test_team_router.py:188-200` if no-Team runtime fallback is intentionally removed; otherwise the route and runtime contracts would diverge.
- Backend storage round-trip: `tests/unit/infra/test_team_storage.py:242-320` confirms member persistence but currently has no mode assertions; no member mode is stored, so the useful assertion is that the persisted member remains ID/metadata-only and backend manager prevents Fast IDs from reaching storage.
- Team LLM tool: `tests/infra/tool/test_team_tool.py:168-331` covers create/update delegation and invalid IDs but has no mode gate. Add a Fast-Persona rejection test at the manager boundary (the tool should return its existing structured error wrapper).
- Team runtime harness: `tests/unit/agents/test_team_router.py:12-176` and `tests/agents/test_disabled_skills_config_propagation.py:642-820` cover roster and role-subagent construction but never assert Persona mode. Add a test that a Search preset reaches the role subagent and a Fast preset is rejected before `create_deep_agent`.
- Frontend Team builder: `frontend/src/components/team/__tests__/teamBuilderPresentation.test.ts:75-101` checks general builder surfaces only. Add a source or component test that Fast presets are excluded while Search presets remain selectable, and verify save payload still contains the selected preset ID.
- Frontend chat: existing `frontend/src/hooks/useAgent/__tests__/teamRequestScoping.test.ts:10-21`, `frontend/src/components/chat/__tests__/teamSelectorPlacement.test.ts:34-78`, and `frontend/src/components/chat/__tests__/welcomeTeamGallery.test.ts:14-72` cover routing/picker placement but not send blocking when Team ID is absent. Add a focused gate test around the send control/callback.

## Caveats / Not Found

- No external references were required; repository code and local specs are sufficient. The Team runtime uses DeepAgents through the existing `create_deep_agent` integration; the exact third-party version is not needed to identify the gate because the relevant call site is local (`src/agents/team_agent/nodes.py:616-626`).
- `TeamMember` does not persist a mode snapshot. A later Persona edit from Search to Fast changes the effective mode seen by `use_preset`; runtime validation must therefore re-check the current Persona on every Team resolution. Conversely, storing a copied mode field would create a second source of truth and is not needed for this request.
- `TeamManager._hydrate_member_display_metadata` and `validate_team_members` use raw `PersonaPresetStorage.get_by_id` (`src/infra/team/manager.py:34-58`, `:198-215`), while runtime prompt loading uses `PersonaPresetManager.use_preset` with visibility checks (`src/agents/team_agent/nodes.py:215-224`, `src/infra/persona_preset/manager.py:352-375`). This means save-time validation must choose an owner-scoped manager lookup rather than copying the raw storage pattern blindly.
- Current tests intentionally codify no-Team fallback, and current TeamAgent docstrings/comments describe fallback behavior (`src/agents/team_agent/nodes.py:88-126`, `src/agents/team_agent/graph.py:42-46`). Removing that fallback requires updating both tests and the runtime contract; merely adding a frontend gate would leave direct callers able to start a Team-mode request without a Team.
- Team list/picker APIs do not expose a computed `available` flag. Whether empty/no-active Teams should be excluded at list time or shown with a repair/create action is not answered by the repository; the backend runtime's existing definition is the only available answer.
- No history migration or compatibility branch is needed per task constraints; stored Team members have no mode field to migrate.
