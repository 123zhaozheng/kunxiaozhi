# Research: OpenSandbox capacity UX map

- Query: Map the implementation boundaries for rejecting OpenSandbox capacity exhaustion, preserving the chat draft with one modal, and adding an admin inventory/action view.
- Scope: internal
- Date: 2026-08-19

## Findings

### Capacity rejection must be a preflight boundary

- Search-agent sandbox acquisition is in `src/agents/search_agent/nodes.py:450-476`; team-agent acquisition is in `src/agents/team_agent/nodes.py:273-295`. Both emit `sandbox:starting` before `SessionSandboxManager.get_or_create`, and convert acquisition exceptions into `sandbox:error` before re-raising (`search_agent/nodes.py:466-510`, `team_agent/nodes.py:286-322`). Raising a capacity error there therefore follows the normal failed-run path.
- `SessionSandboxManager.get_or_create` dispatches OpenSandbox at `src/infra/sandbox/session_manager.py:488-525`. A binding reconnect is attempted at `:1031-1066`; new provider creation is synchronous inside `run_blocking_io` at `:1078-1089`, then the Mongo binding is saved at `:1090-1098`. Capacity admission should be an explicit manager/provider operation that can run before creation, while preserving the existing reconnect path for already-bound users.
- The chat route creates `session_id`, `run_id`, a trace id, and task context before dispatch (`src/api/routes/chat.py:424-465`). The queued path creates the session and persists `user:message` immediately (`:489-524`), and both direct/ARQ submissions pass `write_user_message_immediately=True` (`:552-598`). A capacity exception raised only inside an agent node cannot satisfy “no chat message/partial stream”. It will also enter `TaskExecutor._handle_generic_error`, which marks the session failed and writes an error event/notification (`src/infra/task/executor.py:321-371`).
- Recommended boundary: after request validation/agent resolution but before creating a durable task/session/message, call a capacity admission check for sandbox-capable agents. If unavailable, return HTTP `503` with a structured detail such as `{ "error": "sandbox_capacity_unavailable", "message": "沙盒资源暂满，请稍后重试" }`; do not enqueue, persist the user message, emit SSE, or create a run. The check must be race-safe with creation (admission reservation or a provider-side create attempt that is rolled back), otherwise two preflights can both pass.
- The fast agent is excluded: `src/agents/fast_agent/graph.py:48-55` declares `_supports_sandbox = False`, and `src/agents/fast_agent/context.py:188-193` excludes sandbox tools when `agent_id == "fast"`. Capacity rejection must not run for fast-agent requests.
- Scope is deliberately rejection-only: no durable queue, request persistence, queue position, or automatic resume. Existing general concurrency queue behavior in `src/api/routes/chat.py:467-550` is a separate concern and should not be reused for sandbox capacity.

### Frontend draft preservation and unified modal

- `frontend/src/hooks/useAgent.ts:574-627` creates optimistic user/assistant messages and sets loading before `sessionApi.submitChat`; the generic catch at `:817-840` turns the optimistic assistant message into an error. Capacity rejection should be detected by a stable machine-readable code, not by matching `503` or translated text, and should bypass this generic assistant-error mutation.
- `frontend/src/components/chat/ChatInput.tsx:426-441` calls `onSend(trimmed, ...)`, then immediately pushes history, clears the input, and clears attachments. `ChatInputProps.onSend` currently returns `void` (`frontend/src/components/chat/chatInputTypes.ts:15-20`). To preserve the draft, change the send contract to return a typed result/Promise (or provide a rejection callback) and clear the input only after admission succeeds; on `sandbox_capacity_unavailable`, keep the original draft/attachments and open one capacity modal.
- `ChatInput` already renders `ConfirmDialog` at `frontend/src/components/chat/ChatInput.tsx:847+`; the reusable dialog is a portal with focus, Escape handling, body-scroll lock, and `danger`/`warning`/`info` variants (`frontend/src/components/common/ConfirmDialog.tsx:7-17`, `:37-62`, `:85-145`). Add a dedicated informational capacity modal there (or a sibling chat-level modal), with the single approved message `沙盒资源暂满，请稍后重试`; do not emit a toast plus modal.
- `authFetch` currently discards structured error fields and throws a translated `Error` (`frontend/src/services/api/fetch.ts:92-105`). Preserve `status` and `detail.error` in a typed API error (or add a submit-specific parser) so `useAgent` can branch only on `sandbox_capacity_unavailable`. Existing translation behavior can remain the fallback for all other errors.
- Existing visibility-aware refresh patterns are `useLoginIdleSession` (`frontend/src/hooks/useLoginIdleSession.ts:23-40`, checks `document.visibilityState` and refreshes on `visibilitychange`) and `useAgent` (`frontend/src/hooks/useAgent.ts:215-227`, refreshes when the page becomes visible). `frontend/src/components/persona/useWeComStatusPoll.ts:35-81` scopes polling to an enabled mounted view, performs an immediate fetch, installs/cleans an interval, and guards stale updates; its current interval is 15 seconds (`:6`), so a new sandbox inventory poll should use the requested 10 seconds and add an explicit visibility guard plus immediate refresh on becoming visible.

### Admin inventory, polling, actions, and permissions

- Backend list-route conventions use bounded `skip`/`limit`, return a list plus `total`, and apply a permission dependency. Examples: `src/api/routes/notification.py:34-42` (`notification:manage`) and `src/api/routes/role.py:19-30`; settings routes use `require_permissions("settings:manage")` (`src/api/routes/settings.py:45-62`, `:95-99`). A new OpenSandbox admin route should keep the API key server-side and use the existing settings-management permission (or a newly registered, consistently enforced sandbox permission), with bounded pagination and a single-row action endpoint.
- Frontend API wrappers follow `authFetch` + `API_BASE` and serialize pagination parameters. `frontend/src/services/api/notification.ts:21-32` is the closest admin list example; `frontend/src/services/api/user.ts:14-36` uses `skip`, `limit`, and search. The shared `frontend/src/components/common/Pagination.tsx:9-14`, `:31-45`, `:62-97` accepts 1-based page/pageSize/total and calls `onChange`.
- `frontend/src/components/panels/UsersPanel.tsx:349-401` demonstrates server pagination state (`page`, `total`, fixed page size), a `loadData` callback keyed by page/search, and reset-to-page-one on search (`:403-406`). `frontend/src/components/panels/MemoryPanel/index.tsx:39-100` demonstrates fetch/loading/error state and a refresh callback reused after mutations; delete handlers refetch after success (`:106-117`).
- Destructive row actions should use `ConfirmDialog` with `variant="danger"` and `loading`, as in `UsersPanel.tsx:715-727`; non-destructive action failures can use a toast, but the row should be refreshed immediately after pause/resume/renew/kill. `WeComNetworkSettings.tsx:50-99` is the reference for action-specific loading state, clearing stale results before an action, and refreshing displayed state after save/test.
- Proposed inventory columns should distinguish provider state (`Running`, `Paused`, `Stopping`, `Terminated`, `Failed`), `sandbox_id`, metadata/user binding, `created_at`, `expires_at`, and last transition/reason. OpenSandbox list/get/metrics details are documented in the companion research artifact; aggregate server capacity is not supplied by the SDK, so capacity status must be derived from the provider/deployment contract and labeled accordingly.
- Proposed admin action semantics: pause/resume/renew are reversible/provider-defined and should poll the row until the requested state; kill/delete is irreversible and requires the danger confirmation. Refresh only the affected row after completion, then reconcile the current page/total if the row leaves the selected filter.

### Exact affected/new file map

- Backend existing: `src/api/routes/chat.py` (preflight before task persistence), `src/infra/sandbox/session_manager.py` (capacity/admission and provider listing/action adapter), `src/api/main.py` (register admin router), `src/kernel/exceptions.py` or a sandbox-domain exception module (stable capacity error), and `src/kernel/schemas/` (list/action response models).
- Backend proposed new: `src/api/routes/opensandbox_admin.py` (permissioned paginated inventory plus row actions) and, if not kept in the manager, `src/infra/sandbox/opensandbox_admin.py` (server list/status/metrics/action service). Do not expose `OPENSANDBOX_API_KEY` to the frontend.
- Frontend existing: `frontend/src/hooks/useAgent.ts`, `frontend/src/components/chat/ChatInput.tsx`, `frontend/src/components/chat/chatInputTypes.ts`, and `frontend/src/services/api/fetch.ts` for typed capacity rejection and draft/modal flow; `frontend/src/components/layout/UserMenu.tsx` and `frontend/src/components/layout/AppContent/TabContent.tsx` if a dedicated admin tab is added.
- Frontend proposed new: `frontend/src/services/api/opensandbox.ts`, `frontend/src/types/opensandbox.ts`, and `frontend/src/components/panels/OpenSandboxPanel.tsx` (inventory, 10-second visible polling, manual refresh, row actions, and pagination). Add locale keys in the existing i18n locale files for the modal, state labels, action confirmations, and errors.

### Focused verification targets

- Backend tests: preflight rejects capacity before task/session/message persistence for search/team, fast agent bypasses the check, stable `503` error shape is returned, and admission races do not over-allocate. Add provider-service tests with mocked SDK/HTTP for pagination, state polling, row actions, and API-key isolation; retain existing OpenSandbox manager/factory tests (`tests/infra/test_session_sandbox_manager.py:99-247`, `tests/infra/test_sandbox_factory.py:56-153`) and backend wrapper tests (`tests/infra/backend/test_opensandbox_backend.py:268-292`).
- Frontend tests: typed `authFetch` error preserves `sandbox_capacity_unavailable`; `useAgent` does not mutate optimistic assistant state for this code; `ChatInput` keeps the draft/attachments and opens exactly one modal; the inventory poll starts immediately, repeats every 10 seconds only while visible/enabled, cleans up, supports manual refresh, and refreshes only the acted row. Run the focused frontend test command used by the package plus backend `pytest` targets for chat/task and sandbox manager/adapter modules.

## Caveats / Not Found

- The current architecture has no capacity/list abstraction in `SessionSandboxManager`; adding an admission operation is a design change, not a wiring-only route. OpenSandbox provider capacity may be deployment-specific, and the SDK does not guarantee a server-wide aggregate load endpoint.
- Current `useWeComStatusPoll` is 15 seconds and does not check document visibility; it is a lifecycle template, not evidence that the requested 10-second visibility-scoped behavior already exists.
- No live OpenSandbox server was contacted or mutated. Provider state transitions, quotas, and action availability must be validated against the deployed server OpenAPI/version.
