# Investigation Design

## Boundaries

本任务不实现修复，只完成一轮可复核的强审查。审查边界覆盖事件写入、Mongo trace 文档生命周期、历史读取 API 契约、前端历史重建与测试，但不修改业务代码或真实数据。

## Evidence Flow

1. 以当前工作区 diff 确定实际修改，而非依赖口头描述。
2. 从前端 `loadHistory` 逆向追踪至存储聚合，并从 Presenter/worker 正向追踪 trace 创建与事件落库。
3. 将配置上限、API 上限、读取 probe、写入 `$slice` 和前端响应类型视为一个跨层契约整体审查。
4. 通过定向测试验证现有单元行为，再由独立检查代理复核未覆盖的并发、排序和数据安全问题。

## Review Contracts

- 每项 finding 必须包含严重程度、置信度、文件与行号、触发条件和影响。
- “真实数据中存在两个文档”可引用为用户提供的已测事实；其产生原因只有代码能够支持的强推断，除非取得数据库时间线或索引日志，否则不得标记为完全证实。
- 读路径不应承担不可逆的数据修复；任何清理方案必须可审计、限定 session、处理事件并集并避免与活跃写入竞态。
- 历史读取不得在截断时静默伪装为完整结果；上限、分页或 `has_more/events_limited` 必须形成端到端契约。

## Risks and Rollback

- 最大风险是调查过程中误触真实 MongoDB；所有验证限制为代码、mock 测试和只读 git 检查。
- 工作区有大量无关脏改动；只允许写 Trellis 任务文档。
- 若检查代理发现研究证据不成立，回到研究阶段修订报告，不进入业务代码修改。

## Deferred Implementation Choices

- 分页采用 cursor、按 trace 分页还是物化消息快照。
- 重复文档清理采用离线迁移、管理命令还是一次性脚本。
- stale-running 的权威终止条件与 active-writer 判定方式。

这些属于后续修复任务的产品/架构决策，本调查只给优先级建议。
