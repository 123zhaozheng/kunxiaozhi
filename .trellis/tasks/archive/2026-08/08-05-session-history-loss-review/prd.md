# 调查刷新后会话回复丢失与重复 trace

## Goal

基于仓库代码、测试、变更差异与可用历史记录，独立验证会话 `994c3a6b-04e6-484d-951d-2f72877d7869` 刷新后回复大量丢失的因果链，并强审现有修复是否正确、安全、完整。当前阶段只调查和给出结论，不修改业务代码。

## Background

用户提供了以下待独立验证的调查结论：

- 历史回放链路为前端 `sessionApi.getEvents()` → API 路由 → `dual_writer.read_session_events()` → `trace_storage.get_session_events()`。
- 存储层默认读取上限 1000，导致真实含 7909 个事件的会话仅返回前 1000 个事件，回复正文无法完整重建。
- 同一个 `trace_id` 存在一个完整 trace 文档和一个仅含 `token:usage` 的 running 空壳文档。
- 已有改动包括前端显式传 `limit=10000`、存储上限提升至 10000、读路径惰性去重，以及 stale-running 惰性修正。
- 用户报告相关测试、lint、类型检查和真实数据验证均已通过；本任务需核实这些结果及其覆盖范围。

独立代码研究已确认：旧的 1000 事件读取默认值是本次刷新后内容缺失的直接原因；但现有 10000 调整只移动阈值，且读路径惰性去重存在确认的数据删除风险。详细证据见 `research/session-history-loss-review.md`。

## Requirements

- R1：从前端历史加载到 MongoDB 聚合查询逐层核对参数、排序、过滤、截断和响应元数据，确认直接根因与任何并行丢失路径。
- R2：检查当前工作区实际 diff，而不是只按用户描述评判；区分已提交代码、未提交修复和无关脏改动。
- R3：追踪 `create_trace` 的全部生产调用方、并发模型、索引创建与异常处理，判断重复 `trace_id` 文档的可证成因及剩余不确定性。
- R4：审查惰性去重算法的保留规则、并发安全性、数据丢失风险、读路径写副作用、性能与异常可观测性。
- R5：审查 10000 硬上限是否只是延后故障；核对 `events_limited` / `events_limit` 在后端和前端的契约及分页能力。
- R6：审查事件排序稳定性、跨 trace 合并、重复事件语义，以及只按 `event_count` 选文档是否可能保留错误副本。
- R7：核对新增/修改测试是否真正覆盖生产查询、边界值、重复文档、并发与超限行为；在不改代码前提下运行必要的定向验证。
- R8：输出按严重程度排序、带文件与行号证据的 review findings，并明确区分“已证实”“高概率推断”“尚无证据”。

## Acceptance Criteria

- [ ] 给出页面刷新后回复丢失的完整、可复核因果链，并确认用户提出的主因是否成立。
- [ ] 对四项现有修复逐项判定：正确、部分正确、错误或存在高风险副作用。
- [ ] 对重复 trace 的产生原因给出代码证据；无法唯一确定时列出候选路径及验证办法，不把推测写成事实。
- [ ] 至少覆盖读取上限、响应截断提示、分页、排序、重复事件、数据删除安全性、索引有效性和并发竞态。
- [ ] 定向测试或只读验证结果可复现；不触碰与本调查无关的 53 项工作区改动。
- [ ] 最终报告先列 findings，再给根因解释和建议修复优先级。
- [ ] 由独立 `trellis-check` 审查者复核研究结论、当前 diff 和定向测试，避免单一研究者误判。

## Out of Scope

## Constraints

- 数据库中的惰性去重可能已经改变该会话原始证据；需要结合代码、日志、历史对话和测试判断。
- 任何线上/真实数据写操作均不在授权范围内。

## Technical Notes

- 当前最严重风险不是 10000 上限本身，而是 `dedup_duplicate_traces` 在普通读取请求中永久删除 Mongo 文档，并且删除条件未包含 `session_id`。
- 重复 trace 的最强代码解释是：同一业务 trace 会由多个 Presenter 实例重复调用 `create_trace`，而唯一索引初始化是 fire-and-forget；索引未就绪或创建失败时，应用级逻辑没有原子防重。
- API 在最大值 10000 时请求 `limit + 1`，但存储层又 clamp 回 10000，因此无法正确设置 `events_limited=true`；前端类型和加载逻辑也未消费该字段。
- 单 trace 写入本身还有 `SESSION_MAX_EVENTS_PER_TRACE=10000` 的 `$slice`，即使读取分页完善，旧事件仍可能已在写入阶段被永久裁掉。
