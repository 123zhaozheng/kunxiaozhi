# Research: Trace event write/read timeline and refresh gaps

- Query: Reconstruct Presenter -> DualEventWriter -> Redis/Mongo -> history API timing, including batching, completion filters, retries, stale-running recovery, rollout modes, and crash behavior; rank explanations for events disappearing on refresh and reappearing later.
- Scope: internal
- Date: 2026-08-07

## Findings

### Files found

- `src/infra/writer/presenter_storage.py` — Presenter trace creation, per-event persistence, completion ordering, and exception handling.
- `src/infra/session/dual_writer.py` — Redis Stream write/read, Mongo in-memory buffer, delayed/batch flush, immutable/legacy write-mode branching, and session history dispatch.
- `src/infra/session/trace_storage.py` — trace metadata lifecycle, immutable event upserts, legacy aggregation/page reads, completion filters, and stale-running CAS recovery.
- `src/api/routes/session.py` — authenticated session history endpoint; always requests `completed_only=True`.
- `src/api/routes/share.py` — public-share history endpoint; also requests `completed_only=True`.
- `src/infra/task/executor.py` — normal/error/cancel completion ordering and terminal Redis TTL shortening.
- `src/infra/task/startup_cleanup.py`, `src/infra/task/manager.py`, `src/api/main.py` — startup-only stale trace recovery wiring.
- `src/infra/runtime_services.py` — shutdown Mongo-buffer drain.
- `frontend/src/hooks/useAgent.ts`, `frontend/src/services/api/session.ts` — refresh history reset/pagination and the frontend's 1,000-event request default.
- `.trellis/spec/backend/trace-event-storage.md`, `session-history-pagination.md`, `trace-stale-recovery.md`, `trace-uniqueness-readiness.md` — contracts matching the implementation constraints.

### Code-accurate write timeline

1. `StoragePresenterMixin.save_event` awaits `_ensure_trace()` before writing (`presenter_storage.py:169-170`). Trace creation itself awaits index readiness and atomic/idempotent trace creation (`presenter_storage.py:126-145`; `dual_writer.py:240-264`). A readiness or identity error is re-raised, while other save errors are only logged (`presenter_storage.py:206-209`).
2. `DualEventWriter.write_event` allocates one `event_id` immediately and, in `dual`/`event_store`, allocates a session sequence before Redis (`dual_writer.py:282-289`). It serializes the payload and awaits `_write_to_redis_direct` first (`dual_writer.py:291-300`). Redis success is not a transaction with Mongo: `_write_to_redis_direct` catches failures and returns `False` (`dual_writer.py:626-653`), while the caller still proceeds to Mongo buffering.
3. For a traced event, the same call then waits for room in `_mongo_buffer` and appends `(trace_id, ..., event_id, seq)` (`dual_writer.py:301-316`). Buffer pressure backpressures by calling `flush_mongo_buffer`; it does not evict old events. A post-flush full buffer raises (`dual_writer.py:317-321`).
4. A buffer at/above 200 events triggers an awaited flush (`dual_writer.py:322-333`; `_MONGO_BATCH_SIZE=200` at `dual_writer.py:46-48`). Otherwise the first event schedules one delayed flush after 1.0 second (`dual_writer.py:326-330`, `349-356`). Therefore Redis can contain an event for roughly up to the delay (or until a 200-event threshold/completion/explicit flush) while Mongo has no durable event yet.
5. `_do_flush` detaches the whole current buffer before doing I/O (`dual_writer.py:391-400`). It checks readiness, validates one session/run identity per trace, and ensures each trace exists before persistence (`dual_writer.py:404-453`). In `dual`/`event_store`, it writes immutable `trace_events` first (`dual_writer.py:491-531`), using `TraceStorage.write_trace_events` `$setOnInsert` upserts keyed by `(session_id, trace_id, event_id)` (`trace_storage.py:217-241`). Metadata `event_count` repair is best effort after immutable writes (`dual_writer.py:499-526`).
6. `legacy` mode only builds a `$push`/`$slice:-max_events` bulk update (`dual_writer.py:546-553`; default max 10,000 from `dual_writer.py:58-60`). `dual` then additionally builds and executes that compatibility array update (`dual_writer.py:533-545`, `555-569`); `event_store` skips legacy arrays entirely. A failed immutable preflight/write or legacy bulk write puts the original batch back at the front and sets `_flush_event` (`dual_writer.py:422-431`, `448-453`, `527-531`, `562-569`). The scheduled-task callback logs failures (`dual_writer.py:337-347`); setting the event alone does not start a retry, so another event, explicit flush, or shutdown drain is needed to retry.
7. `Presenter.complete` awaits token-usage insertion, then `flush_mongo_buffer`, then `complete_trace` status update (`presenter_storage.py:239-253`). Thus on the successful path event durability precedes terminal trace metadata. But a generic flush/status exception is swallowed/logged (`presenter_storage.py:265-269`), so a failed flush can leave the trace `running` while the task executor proceeds to mark the session completed (`executor.py:180-187`).

### Redis Stream behavior and TTL

- Redis stream keys are `session:{session_id}:run:{run_id}:events` (`dual_writer.py:235-238`). A successful xadd installs/refreshes `SSE_CACHE_TTL` (default 86,400 seconds, `base.py:151-155`) initially and at a bounded refresh interval of at most 300 seconds (`dual_writer.py:70-72`, `626-641`). This TTL is only live-stream retention; the history API never reads Redis.
- A terminal executor path shortens the run stream to 60 seconds (`executor.py:27`, `373-392`). Normal success calls this after session completion notification (`executor.py:180-188`); error/cancel paths do likewise (`executor.py:257-262`, `314-319`, `367-371`). Mongo history is unaffected by this expiration.
- `read_from_redis` first replays the complete stream with paged `XRANGE` (500 entries by default), then blocks with `XREAD` (`dual_writer.py:684-717`, `751-779`). It returns as soon as it yields `complete`, `error`, or `done` (`dual_writer.py:713-715`, `774-779`). Consequently a late event written after a `done` event is not delivered by a fresh SSE replay even if it remains in the stream.
- `_flush_redis_buffer` is a compatibility no-op (`dual_writer.py:580-582`); there is no Redis-to-Mongo replay queue. Redis-first success does not prove Mongo durability, and Redis failure does not prevent Mongo buffering.

### History API and filters

- Session and share GET handlers both call `read_session_events_page(..., completed_only=True)` (`session.py:320-330`; `share.py:319-335`). The session handler explicitly documents that running-trace events are intentionally omitted so the UI uses the stream instead (`session.py:320-322`). There is no Redis fallback in these GET paths.
- Legacy reads add `status: {"$ne":"running"}` (`trace_storage.py:1334-1345`), so any non-running status is admitted. Immutable `event_store` reads fail closed: they first collect trace IDs whose metadata status is explicitly `completed` or `error`, and return no event for unknown/missing/running metadata (`trace_storage.py:252-278`). Merge mode reads both stores with the same `completed_only` flag and merges by stable event identity (`dual_writer.py:853-890`).
- The immutable page reports `history_complete=not has_more` (`trace_storage.py:295-320`), while legacy and merge pages always report `history_complete=False` because retained arrays do not prove durable completeness (`trace_storage.py:1491-1552`; `dual_writer.py:919-948`). This is an incomplete-history signal, not a temporary retry mechanism.
- Frontend history loading clears current messages before fetching (`useAgent.ts:300-325`), requests events in parallel with status (`useAgent.ts:385-408`), and only applies the result if the request is still current (`useAgent.ts:295-299`, `409`). The loader accumulates cursor pages and preserves prior pages on later-page failure/abort (`session.ts:65-125`). Each page request defaults to 1,000 (`session.ts:49`, `275-309`), despite the comment saying the backend can be capped at 10,000.

### Completion, late-event, and stale-running ordering

- Normal agent graph processing emits `done` into storage before the executor calls `presenter.complete` (`src/agents/core/base.py:532-558`; `executor.py:177-184`). `save_event` awaits the Redis xadd/buffer append for each event (`presenter_storage.py:188-205`), but Mongo durability can still be pending until the delayed/batch flush or `complete`.
- Generic failures first flush old events, call `presenter.complete("error")`, and only then write the direct `error` event (`executor.py:337-365`). Cancel/interrupted paths emit `done` and complete the trace, then write a direct `error` event (`executor.py:223-256`, `281-313`). This means a terminal status can be visible to history before the final error event reaches Mongo; a later flush can make that event appear. Since Redis replay stops at `done`, the late error is also missed by a newly reconnecting SSE reader.
- Startup cleanup invokes stale trace reconciliation after task cleanup under its lease (`startup_cleanup.py:383-394`; callback wiring `manager.py:163-184`). Recovery only scans old `status=running` traces (`trace_storage.py:1151-1197`), checks the current run and strict heartbeat, and CASes a terminal status only with terminal task/event evidence (`trace_storage.py:1214-1280`). A live heartbeat/current active run keeps the trace running; a successful recovery changes it to `completed` or `error` (`trace_storage.py:1227-1245`).
- Shutdown drains the process-local Mongo buffer (`runtime_services.py:44-47`, `156-162`), but a process crash/restart loses that in-memory buffer. Redis may survive until its TTL, but history reads still cannot see those unflushed events. Immutable events already written to `trace_events` survive restart; legacy-array writes or pending in-memory batches do not necessarily.

### Ranked mechanisms for “refresh lost it, later it came back”

1. **Most likely: `completed_only` race with an active run.** The stream showed the event immediately, but refresh clears the UI and the history GET deliberately excludes the still-`running` trace (`session.py:320-328`; legacy filter `trace_storage.py:1342-1345`; immutable filter `trace_storage.py:252-278`). After `presenter.complete` updates status, the same Mongo events become eligible and the next refresh reconstructs them. If completion failed or was delayed, startup stale recovery can later flip the trace terminal and make the already-buffered events reappear (`trace_storage.py:1186-1245`).
2. **Mongo write-behind window.** Redis xadd is awaited before Mongo buffering, while Mongo waits up to 1 second or 200 events (`dual_writer.py:291-333`, `349-356`). A refresh during this interval sees neither event in history, although SSE has it; the next flush makes it available (still subject to the running filter). Completion explicitly drains the buffer, so it commonly appears just after the run ends (`presenter_storage.py:239-252`).
3. **Flush failure/requeue and swallowed completion error.** Bulk/preflight failures requeue the batch (`dual_writer.py:422-453`, `527-569`), but the scheduled callback only logs and does not independently retry; `Presenter.complete` swallows the flush exception (`presenter_storage.py:265-269`). A later event/explicit flush/shutdown can persist the batch; stale recovery can make a formerly running trace visible after the task has otherwise ended.
4. **Late error event after terminal status.** Error/cancel handlers mark the trace terminal before writing their direct error event (`executor.py:223-256`, `337-365`). A refresh can therefore return the completed prefix, and a later Mongo flush adds the error. In Redis, a reconnect may stop at the earlier `done`, so stream and history can disagree.
5. **Legacy/dual mode source timing or retry asymmetry.** In dual mode immutable events are written before the legacy array (`dual_writer.py:491-545`). If the legacy bulk fails, the immutable event can already be visible in `event_store`/merge mode while the legacy array is not; retrying the whole batch is idempotent for immutable documents but `$push` can duplicate legacy entries (`trace_storage.py:217-241`; `dual_writer.py:555-569`). This is less likely to explain a normal temporary disappearance, but can explain mode-dependent reappearance/duplicates.
6. **Read cap / retained-array limits.** Legacy mode defaults to 1,000 events per API page (`trace_storage.py:1346-1355`, frontend `session.ts:285-287`) and legacy writes retain only the last 10,000 per trace (`dual_writer.py:547-553`). This causes durable omissions rather than a clean temporary gap, unless a later mode switch/backfill changes the source; treat it as a secondary explanation for long-session refresh reports.

## Caveats / Not Found

- No history GET path reads Redis or waits for the Mongo buffer; the only Redis consumer is the live SSE stream. Therefore “Redis has it, history does not” is expected during both the buffer window and any running-trace filter window.
- There is no per-event Mongo TTL. Redis TTL affects live replay only; Mongo/event-store documents persist unless explicitly migrated/deleted elsewhere.
- `legacy`, `dual`, and `event_store` are runtime settings (`base.py:65-70`), so observed behavior depends on deployment flags. Defaults are `legacy` write/read, not immutable event-store mode.
- A process shutdown attempts a final flush, but a crash has no recovery path for `_mongo_buffer`; only data already written to Mongo (legacy array or `trace_events`) survives. Redis retention cannot backfill Mongo because `_flush_redis_buffer` is a no-op.
- The code does not expose a single cross-store commit timestamp or durable “Mongo pending” marker. Exact disappearance duration therefore requires correlating Redis xadd, flush logs, trace status, and API request time.
